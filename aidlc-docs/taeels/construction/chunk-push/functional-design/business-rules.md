# U7 `chunk-push` — 불변식

```text
   유닛    chunk-push (U7) · 답 여덟이 전부 A
```

**세는 것으로 지킨다.** 각 줄에 무엇이 재는지를 적는다.

---

## 1. 실행을 안 막는다 — 이 유닛의 첫째 규율

```text
   R1   Write 는 언제나 len(p), nil 을 낸다.  오류를 0 번 낸다
        왜 — io.MultiWriter 는 한 갈래가 오류를 내면 거기서 멈춘다.
        업로더가 오류를 내면 링까지 끊기고 제어판의 카드도 함께 죽는다
   R2   Write 는 네트워크를 0 번 기다린다.  버퍼에 넣고 바로 돌아온다
        재는 법 — Mediator 를 막아 놓고 Write 의 시간을 잰다
   R3   버퍼가 넘쳐도 Write 는 여전히 바로 돌아온다.  받기만 안 한다
   R4   업로더 고루틴이 패닉해도 노드가 안 죽는다 (recover)
```

**R1 과 R2 가 W-b 의 U2 가 실측으로 밟은 자리다** — 변이 ⑤ 에서 `Write` 가 영영
막혀 **실패가 아니라 600초 멈춤**으로 빨갰다. **업로더는 네트워크라 더 세다.**

---

## 2. 시도 — 이 유닛의 착수를 막던 자리

```text
   R5   노드는 step.Attempt 를 **그대로** 보낸다.  +1 을 안 한다
        왜 — 저장소 전체가 0 을 첫 시도로 쓴다 (store/claim.go:156 ·
        원장의 %02d.%d-이름 · 산출물 이름).  한 자리만 다른 수를 쓰면 갈린다
   R6   Mediator 가 attempt 0 을 받는다.  api.go 의 `attempt <= 0` 을 `< 0` 으로
        재는 법 — attempt=0 으로 PUT 하면 200 이다.  **그 줄이 저장소에 0 이었다**
   R7   응답의 Attempt 가 내 것보다 크면 **내 청크가 버려진 것**이다.
        오프셋을 안 옮기고 이 업로더는 멈춘다
   R8   **걷었다.** 「Attempt 를 Total 보다 먼저 본다」였는데 공허한 규칙이다 —
        R7 이 새 시도를 보면 **멈추므로** 그 뒤에 오프셋을 읽는 자리가 0 이다.
        멈추는 것이 순서를 삼킨다.  변이로 실측했다 (code-summary 4.1)
```

---

## 3. 오프셋

```text
   R9    오프셋은 **보내는 고루틴의 지역 변수**다.  구조체 필드가 아니다.
         Write 가 오프셋을 볼 일이 0 이다 — 공유 상태가 하나 준다
   R10   오프셋의 진실은 서버가 준 X-Enode-Log-Bytes 다.  노드가 보낸 바이트를
         세지 않는다 (api.go 의 putProgress 주석이 이미 그렇게 적었다)
   R11   실패한 청크는 **버퍼 앞에 도로 붙인다.**  다음 주기에 새 바이트와 함께
         한 번에 간다 — 청크 경계가 달라져도 서버가 이어 붙이므로 상관없다
```

---

## 4. 멈추는 두 자리 — 서로 다른 것이다

```text
   R12   서버 상한(Capped)에 닿으면 더 안 올린다.  **실행은 계속된다**
   R13   상한의 표시는 **서버가 박는다** (record/progress.go 의 enode.capped).
         노드가 표시를 0 번 짓는다
   R14   버퍼가 넘치면 더 안 올린다.  **표시가 없다** — 넘치는 조건이
         「Mediator 에 못 닿는다」이므로 못 닿는 채로 표시를 보낼 수 없다
   R15   연결이 돌아와도 **재개하지 않는다.**  넘쳐서 버린 바이트가 이미 없으므로
         재개하면 구멍이 생기고 그 구멍에 표시가 없다
```

**R13 과 R14 의 비대칭이 화면의 판정 재료다.** 진행 파일에 `enode.capped` 줄이
있으면 상한이고, 아무 줄 없이 끝나 있으면 노드가 포기한 것이다.

---

## 5. 수명

```text
   R16   업로더의 수명은 **단계 하나**다.  단계마다 새로 만든다 —
         링의 Reset 과 같은 자리 (claim.go:455).  리셋을 잊을 자리가 없다
   R17   단계 끝에 마지막으로 비운다.  그 뒤에 UploadLog(선별본)가 간다 —
         순서를 뒤집으면 봉인 직전의 마지막 문장이 화면에 안 뜬다
   R18   업로더는 링이 붙는 **모든 자리**에 붙는다 — 에이전트(claim.go:794)와
         명령(claim.go:632).  규칙이 하나다: 링으로 가는 것은 Mediator 로도 간다
```

---

## 6. 값과 어휘

```text
   R19   버퍼 상한 **1 MiB**.  상수다 — 조절 손잡이가 아니라 보호라 설정 키를 안 만든다
         CB3 의 10초 정지가 그 안에 들어가야 한다.  **CB3 이 이 값을 실제로 밟는다**
   R20   주기 2초 · 즉시 문턱 64 KiB.  decisions.md 2절.  이 유닛이 안 정한다
   R21   이 유닛이 새 type 을 **0 개** 들인다.  transcript.Kind 일곱이 그대로다
   R22   보내는 것은 하네스 stdout 의 바이트 그대로다.  줄도 안 나눈다 —
         줄 경계는 읽는 쪽(U4 의 as=events)이 이미 판다
```

## 7. 안 건드리는 것

```text
   R23   UploadLog(claim.go:796)의 동작이 안 바뀐다.  쿼리가 다르고 파일이 달라
         두 벌이 안 생긴다
   R24   internal/record 의 diff 가 0 이다 (U3 가 닫았다)
   R25   라우트가 안 는다.  api.go 의 18 그대로 — CB0 을 안 건드린다
   R26   내려받는 쪽(GET)의 diff 가 0 이다.  이 유닛은 PUT 만 한다
```

---

## 8. 잔여 — 이 유닛이 안 닫는 것

```text
   ①  버퍼가 넘쳐 멈춘 것을 **중앙이 알 길이 0 이다.**  화면은 경과가 자라는
      것으로만 안다 (NC-1).  못 닿는 채로 표시를 보낼 수 없어서이고,
      닫으려면 연결이 돌아온 뒤 표시를 미는 길을 새로 파야 한다

   ②  1 MiB 가 실제 출력 속도에 맞는지 안 쟀다.  CB3 의 10초 정지가 잰다 —
      넘치면 그때 올린다

   ③  명령 단계가 수다스러우면 MaxBlobBytes 10 MiB 에 더 빨리 닿는다 (답 2 = A).
      닿으면 R12 가 받는다.  그 빈도는 CB3 · CB6 이 잰다

   ④  전역 한도 120 req/s 를 이 유닛이 갉는다.  함대의 노드마다 2초에 한 번씩
      민다 — U4 가 N1 에서 봉투만 남긴 자리에 실제 부하가 여기서 붙는다.
      **안 닫는다** — 값은 CB6 이 실 함대에서 잰다
```
