# U7 `chunk-push` — Functional Design 계획 (Part 1)

```text
   유닛     chunk-push (U7) · 브랜치 unit/chunk-push
   맡는 것   FR-5 의 노드 쪽 — 도는 동안 원문 청크를 Mediator 로 민다
   지는 게이트  **CB3** (올라간다)
   딛는 게이트  CB1 (U5).  **사용자가 순서를 바꿔 CB1 앞에 선다** — 어긋남으로 적었다
   코드 의존   U2 (tee) · U4 (라우트).  **둘 다 병합됨**
   기준선    05ee710
```

**이 유닛이 Mediator 에 실시간을 실제로 채우는 자리다.** U4 가 받을 길과 낼 길을
둘 다 깔아 놨는데 **보내는 쪽이 없어서** 중앙에 아직 아무것도 안 흐른다.

이 문서는 **묻는 것**이다. 답이 오면 5절의 순서로 산출물 셋을 낸다.

## 0. 이 단계가 닫는 것과 안 닫는 것

```text

             단계 끝의 선별본 업로드 — claim.go:796 이 오늘 그대로 한다
```

## 1. 실측 — 코드가 지금 어떻게 생겼나 (2026-09-16 · 05ee710)

**하나가 이 유닛을 통째로 막는다.** 먼저 적는다.

### 1.1 노드의 첫 시도는 `attempt 0` 인데 Mediator 가 그것을 400 으로 막는다

```go
   store/claim.go:156   Attempt int `json:"attempt,omitempty"` // 0 부터. 재시도면 1 이상.
   api/api.go putProgress   attempt, err := strconv.Atoi(...)
                            if err != nil || attempt <= 0 { fail(w, 400, "invalid attempt") }
```

**탐침으로 실제로 쟀다** (시험을 짓고 돌린 뒤 지웠다).

```text
   attempt=0  ->  400  {"error":{"code":400,"reason":"invalid attempt"}}
   attempt=1  ->  200  X-Enode-Log-Bytes: 93
```

**첫 시도가 대부분이다.** 이대로 업로더를 지으면 **한 바이트도 안 올라가고
CB3 이 통째로 빨갛다.** 「도는 동안 `curl` 로 두 번 부르면 총 길이가 늘어
있다」가 영영 0 이다.

**U4 가 왜 못 봤나** — `internal/api/getlog_test.go` 의 진행 청크 시험 **다섯이
전부 `attempt=1`** 이다. `attempt 0` 갈래를 한 번도 안 밟는다.

```text
   W-b 의 U4 변이 넷째와 같은 모양이다 — 「폴링이 규칙대로 돌면 그 갈래를
   한 번도 안 밟는다」.  그때는 시험을 지어 잡았고 이번에는 안 지었다
```

**`record` 계층은 0 을 정상으로 다룬다** — `progressFile` 이 `%s.%d.log` 로 그냥
쓰고 `maxAttempt` 가 `best, found := 0, false` 로 시작한다. **막는 것은 API 검증
한 줄뿐이다.** 물음 1 이 그 자리다.

### 1.2 링이 붙는 자리가 둘이다 — 에이전트와 명령

```go
   claim.go:794   Transcript: w.transcript(),          // 에이전트 단계
   claim.go:632   sink = io.MultiWriter(&buf, w.ring)  // 명령 단계
```

`unit-of-work.md` 의 U7 절은 **「tee 의 갈래 하나로 꽂힌다」**로 적어 자리가
하나인 것처럼 읽힌다. **실제로는 둘이다.** 물음 2 가 그 자리다.

### 1.3 `transcript()` 가 인자를 0 개 받는다 — 업로더는 넷이 필요하다

```go
   claim.go:313   func (w *Worker) transcript() io.Writer { ... return w.ring }
```

링은 노드에 하나라 인자가 필요 없었다. **업로더는 `runID` · `seq` · `name` ·
`attempt` 를 알아야 한다.** 부르는 자리(claim.go:794)에 `step` 이 있으므로
시그니처를 넓히는 것으로 닿는다 — 겉면이 아니라 비공개 메서드다.

### 1.4 서버가 오프셋의 진실이다 — 이미 그렇게 적혀 있다

```go
   api.go putProgress   // 노드가 이 값으로 자기 오프셋을 맞춘다 — 서버가 진실이다
                        w.Header().Set(headerBytes, strconv.FormatInt(p.Total, 10))
                        w.Header().Set(headerAttempt, strconv.Itoa(p.Attempt))
                        if p.Capped { w.Header().Set(headerCapped, "1") }
```

**받는 쪽이 이미 완성돼 있다.** 노드가 할 일은 그 셋을 읽고 따르는 것이다.

### 1.5 `AppendProgress` 가 늦게 온 앞 시도를 조용히 버린다

```text
   attempt < cur   0 바이트를 쓰고 지금 상태를 낸다.  오류가 아니다
   attempt > cur   앞 시도의 파일을 걷는다 (dropOlderAttempts)
```

**노드가 재시도를 시작하면 앞 시도의 늦은 청크가 200 으로 조용히 사라진다.**
업로더가 그 200 을 성공으로 읽고 오프셋을 옮기면 **안 올라간 바이트를 올라갔다고
민다.** 응답의 `X-Enode-Log-Attempt` 가 그것을 가른다 (1.4). 물음 6 이 그 자리다.

### 1.6 W-b 의 U2 가 같은 함정을 이미 밟았다 — 쓰는 쪽을 막으면 하네스가 멈춘다

`node-stream` 의 변이 ⑤ 가 **「대기열 상한을 빼면 `Write` 가 영영 막힌다」**를
실측했고, 그것이 실패 메시지가 아니라 **멈춤**으로 빨갰다 (600초).

**업로더는 네트워크라 링보다 훨씬 느리다.** 같은 자리를 더 세게 밟는다.
물음 7 · 8 이 그 자리다.

### 1.7 안 만져도 되는 것을 확인했다

```text
   단계 끝 UploadLog   claim.go:796 이 선별본을 logs/ 에 올린다.  파일이 달라 두 벌이
                     안 생긴다 (putLog 의 갈래 주석이 그것을 적는다)
   내려받는 쪽          U4 가 닫았다.  이 유닛은 PUT 만 한다
   internal/record     U3 가 닫았다.  diff 0
   internal/api        U4 가 닫았다 — **물음 1 의 답이 A 면 한 줄이 는다**
```

## 3. 물음 여덟

형식은 `common/question-format-guide.md` 다.

### Question 1 — `attempt 0` 을 어디서 고치나

1.1 이 낸 물음이다. **이 유닛의 착수 조건이다.**

```text
   A   Mediator 가 0 을 받게 고친다 — api.go 의 `attempt <= 0` 을 `attempt < 0` 으로.
       저장소 전체가 0 을 첫 시도로 쓰므로 그 한 줄이 어긋나 있던 것이다.
       U4 의 파일이라 **행렬 밖**이나 병합됐으므로 충돌 0
   B   노드가 `attempt+1` 로 보낸다.  api.go 를 안 건드린다.  대신 진행 파일의
       숫자가 logs/ · 원장(`%02d.%d-이름`)과 **한 칸 어긋난다**
   C   노드가 attempt 0 이면 안 올린다.  첫 시도가 대부분이라 기능이 사실상 안 선다
```

**권장은 A 다.** `store/claim.go:156` 이 **「0 부터」**를 어휘의 정본으로 적었고
원장도 산출물 이름도 그 수를 쓴다. `putProgress` 의 `attempt <= 0` 은 바로 위
`seq <= 0` 을 따라 쓴 것으로 보이는데 **`seq` 는 1 부터이고 `attempt` 는 0 부터다.**
같은 모양의 검사가 다른 뜻을 가진 자리다.

**B 의 대가가 크다** — 같은 단계의 시도 번호가 **자리마다 다른 수**가 된다.
`decisions.md` 가 경계하는 「두 벌로 두면 갈린다」의 교과서적 자리이고, W-b 의
Functional Design 이 **「시도(gen 과 attempt 가 같은 수가 아니다)」**를 갈릴 자리로
이미 이름 붙여 뒀다. 여기서 한 칸을 더 어긋내면 셋이 된다.

**A 가 U4 의 시험도 하나 늘린다** — `attempt=0` 을 밟는 줄이 저장소에 0 이다 (1.1).

### Question 2 — 업로더를 tee 의 어느 자리에 다나

1.2 가 낸 물음이다. 링이 붙는 자리가 둘이다.

```text
   A   링이 붙는 자리마다 단다 — 에이전트(794)와 명령(632) 둘 다.
       규칙이 하나다: 「링으로 가는 것은 Mediator 로도 간다」
   B   에이전트 단계만.  FR-5 가 「하네스 stdout」이라 적었다
```

**권장은 A 다.** 제어판의 카드가 링을 그리므로 **B 를 고르면 중앙이 제어판보다
적게 보인다** — 명령 단계에서 화면 둘이 다른 것을 보이고, 그 비대칭을 화면이
설명할 길이 없다. 규칙을 「링과 같이 간다」 하나로 두면 설명할 것이 0 이다.

**A 의 대가** — 빌드 같은 명령 단계가 수다스럽다. `MaxBlobBytes` 10 MiB 에
더 빨리 닿는다. 닿으면 물음 5 의 규율이 받는다.

### Question 3 — 버퍼가 넘칠 때 무엇을 하나

업로더는 못 보낸 바이트를 들고 있어야 한다 (링은 감기므로 다시 못 읽는다).
Mediator 가 10초 죽으면 그동안의 바이트가 쌓인다.

```text
   A   상한을 두고 넘치면 **더 안 올리고 멈춘다.**  올라간 데까지는 온전하다
   B   넘치면 오래된 것을 버리고 계속 올린다.  **구멍이 생기고 표시가 없다**
   C   무한히 든다.  노드 메모리가 실행을 위협한다
```

**권장은 A 다.** B 의 구멍이 가장 나쁘다 — 중앙의 파일이 **이어 붙은 것처럼
보이는데 가운데가 빠져 있다.** 읽는 사람도 파서도 그것을 구별할 길이 0 이고,
화면은 잘린 JSON 한 줄을 하네스가 깨진 것으로 그린다.

**A 는 「올라간 데까지는 진실」을 지킨다.** 상한에 닿은 것과 같은 모양이라
(물음 5) 규율이 하나로 선다.

[Answer]:

### Question 4 — 오프셋의 진실을 누가 드나

1.4 가 낸 물음이다. 서버가 이미 총 길이를 돌려준다.

```text
   A   서버가 준 X-Enode-Log-Bytes 로 노드가 자기 오프셋을 맞춘다.
       노드는 자기가 몇 바이트 보냈는지를 **안 믿는다**
   B   노드가 보낸 바이트를 세어 자기가 든다.  응답을 안 읽는다
```

**권장은 A 다.** 코드에 이미 그렇게 적혀 있다 — **「노드가 이 값으로 자기
오프셋을 맞춘다 — 서버가 진실이다」** (`api.go` 의 `putProgress` 주석).

**B 가 깨지는 자리** — 상한에 닿아 서버가 일부만 받았을 때, 서버가 시도를
걷었을 때 (1.5), 재전송이 겹쳤을 때. 셋 다 노드의 셈과 서버의 파일이 갈린다.

[Answer]:

### Question 5 — 상한(`MaxBlobBytes`)에 닿으면

서버가 `X-Enode-Log-Capped: 1` 을 준다.

```text
   A   더 안 올리고 노드 로그에 한 줄.  **실행은 계속된다**
   B   계속 시도한다
```

**권장은 A 다.** `unit-of-work.md` 의 U7 절이 그대로 적었고, 계속 시도하면
**닿은 뒤로 매 2초마다 무의미한 왕복**이 함대 규모로 곱해진다 — U4 가 N1 에서
남긴 전역 한도 120 req/s 를 이 유닛이 갉는다.

**표시는 한 번만 박힌다** (`requirements.md` FR-5). 두 번 박으면 화면에
「상한」 줄이 여러 개 선다.

[Answer]:

### Question 6 — 시도가 바뀌면 업로더를 어떻게 하나

1.5 가 낸 물음이다. 늦게 온 앞 시도의 청크는 **200 으로 조용히 사라진다.**

```text
   A   업로더의 수명을 단계 하나로 둔다 — 단계마다 새로 만들고 오프셋 0 에서
       시작한다.  링의 Reset 과 같은 자리다 (claim.go:455)
   B   Worker 에 하나 두고 (seq, attempt) 가 바뀌면 리셋한다
```

**권장은 A 다.** 수명이 단계와 같으면 **리셋을 잊을 자리가 없다.** B 는 리셋
조건을 사람이 맞춰야 하고, 틀리면 앞 단계의 꼬리가 다음 단계의 파일에 붙는다.

**A 를 골라도 1.5 의 자리는 남는다** — 응답의 `X-Enode-Log-Attempt` 가 내가 보낸
것보다 크면 **내 청크가 버려진 것**이다. 그때 오프셋을 옮기면 안 된다.
그 규칙을 `business-rules` 에 적는다.

[Answer]:

### Question 7 — 쓰는 쪽이 네트워크를 기다리면 안 된다

1.6 이 낸 물음이다. W-b 의 U2 가 같은 함정에서 **600초 멈춤**을 봤다.

```text
   A   Write 는 메모리 버퍼에만 넣고 고루틴이 보낸다.  Write 가 절대 안 막힌다
   B   Write 에서 동기로 보낸다
```

**권장은 A 다.** B 는 **하네스의 stdout 이 Mediator 의 응답 시간만큼 멈춘다** —
`cmd.Run` 까지 멈추고, Mediator 가 죽으면 노드의 단계가 통째로 선다.
**관측하는 겹이 실행을 멈추면 그것은 관측이 아니다** (U2 의 링 주석이 같은 말을
적는다).

[Answer]:

### Question 8 — 실패가 노드 로그에 몇 줄로 남나

`requirements.md` FR-5 가 **「실패가 실행이나 링을 막지 않는다」**로 적었다.
안 막는 것과 안 적는 것은 다르다.

```text
   A   연속 실패의 처음 한 번과 회복 한 번만 적는다.  매 실패를 안 적는다
   B   매 실패를 적는다
   C   안 적는다
```

**권장은 A 다.** B 는 Mediator 가 10분 죽으면 **2초마다 한 줄씩 300줄**을 쌓고,
그 300줄이 노드 로그에서 진짜 실패를 덮는다. C 는 **CB3 이 재는 것을 못 보게
한다** — 「PUT 을 한 번 실패시켜도 다음 청크가 이어 붙는다」를 사람이 확인할
자리가 노드 로그다.

## 5. 실행 단계 — 답을 받은 뒤

### 5.1 순서

```text

   2  모순 검사 — 답끼리, 답과 FR-5, 답과 CB3 의 명령

```

### 5.2 모순 검사에서 볼 자리 — 미리 이름으로 든다

```text
   1 x 6    attempt 를 고치는 자리와 시도가 바뀔 때의 규칙이 같은 수를 봐야 한다
   2 x 3    명령 단계까지 올리면 버퍼가 훨씬 빨리 찬다.  상한이 그것을 받나
```
