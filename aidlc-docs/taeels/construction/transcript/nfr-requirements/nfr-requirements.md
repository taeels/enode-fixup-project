# U1 `transcript` — 지켜야 하는 것

**여기는 무엇을 지켜야 하는가다. 어떻게는 다음 자리다.**

값의 근거와 실측은 `plans/transcript-nfr-requirements-plan.md` 1절에 있다.
**이 문서는 그것을 옮겨 적지 않고 결론과 재는 자리만 든다.**

물음 셋의 답은 전부 **A** 다 (2026-09-15).

---

## 1. 답 셋이 정한 것

```text
   Q1 = A   표시 상한의 단위는 바이트다.  상한을 넘지 않는 가장 긴 접두 중
            마지막 룬이 온전한 데까지 남긴다 (2절)

   Q2 = A   사건 증폭의 상한을 U1 이 안 만든다.  입력 상한이 출력을 지고
            증폭 계수를 U4 에 값으로 넘긴다 (5절)

   Q3 = A   「패닉 0」을 FuzzParse 로 잰다.  CI 는 시드만 돈다 (4절)
```

**셋이 서로를 세운다.** Q1 이 불변식 하나를 만들고 Q3 이 그것을 재는 수단을
준다. Q2 가 겉면에 인자를 안 늘려 Q3 의 퍼즈 입력이 바이트 하나와 불리언
하나로 끝난다 — 퍼즈가 탐색할 축이 줄었다.

## 2. 표시 상한 — 바이트이되 룬 경계까지 (Q1 = A)

### 2.1 값

```text
   tool_use 의 입력 요약     200 바이트
   tool_result 의 본문       500 바이트
   그 밖의 Kind             상한이 없다 (FD R8.3)

   자르는 규칙   상한 바이트 자리에서 시작해, 그 자리의 바이트가 UTF-8
                이어바이트인 동안 뒤로 물린다.  최대 세 번이다
   Cut 의 단위   바이트.  룬 경계로 물러난 바이트도 든다
   보장          len(Text) + Cut == 원래 길이
```

**숫자는 팩의 것이고 단위는 이 유닛이 정했다.** 팩 `decisions.md`:50 은
「200자 · 500자」다. 그 갈림을 FD 가 만들었고 이 단계가 닫았다 — 경위는
`functional-design/business-rules.md` 8.1.

### 2.2 무엇을 보장하나 — 자르기가 UTF-8 을 안 깨뜨린다

**입력이 올바른 UTF-8 이면, `Cut > 0` 인 사건의 `Text` 도 올바른 UTF-8 이다.**

```text
   상한이 걸리는 Kind 가 둘뿐이다        tool_use · tool_result
   tool_result 의 Text                 JSON 문자열을 디코드한 것이다.
                                       표준 라이브러리가 잘못된 바이트를 이미
                                       U+FFFD 로 바꾼다 (decode.go:1209-1223)
   tool_use 의 Text                    도구 입력 객체의 원문 JSON 바이트다.
                                       json.Marshal 이 json.RawMessage 를 낼 때는
                                       compact 를 지날 뿐이라 **잘못된 UTF-8 이
                                       그대로 산다** — 실측 (2.2.1)
   그래서 조건이 붙는다                  입력이 올바르면 자르기 앞에서도 올바르고,
                                       룬 경계 자르기가 그것을 유지한다
```

**이 보장이 닫는 문**은 `as=events` 응답의 조용한 손상이다. 바이트로 그냥 자르면
꼬리 룬이 쪼개지고, `json.Marshal` 이 그것을 `U+FFFD` 로 **오류 없이** 바꾼다.
읽는 사람은 파서가 틀린 줄 모른다. **그 문은 그대로 닫힌다 — 닫는 조건이
정확해졌을 뿐이다.**

#### 2.2.1 조건이 붙은 이유 — 실측이 길 둘을 갈랐다

이 절의 첫 판은 「그 둘의 `Text` 는 JSON 을 거쳐 오므로 표준 라이브러리가 두
길에서 이미 고쳐 준다」였다. **길 둘을 각각 돌려 보니 하나가 거짓이다**
(2026-09-15 · `go1.26.6`).

```text
   json.Unmarshal 로 문자열을 받는다        잘못된 바이트가 U+FFFD 가 된다   맞다
   json.Marshal 로 문자열을 낸다            같다                            맞다
   json.Marshal 로 json.RawMessage 를 낸다  **잘못된 바이트가 그대로 산다**   틀리다
```

**값은 한 글자도 안 바뀐다** — 상한도 단위도 자르는 규칙도 그대로다. 바뀐 것은
불변식 F2 의 문장 하나이고, 고칠 자리를 8절 ⑥ 이 든다.

**입력이 이미 깨진 경우에 남는 보장 하나를 따로 적는다** — `len(Text) + Cut` 이
원래 길이와 같고 자른 자리가 `utf8.RuneStart` 다 (FD R8.2). **그것은 입력의
유효성과 무관하게 참**이고, 퍼즈가 그것을 따로 잰다 (4.2).

**고치는 길 셋 중 이쪽만 규칙을 안 깬다.** 자른 뒤 `utf8.Valid` 가 거짓이면
파서가 고치는 길은 마스킹이고 (2.3 · `constraints.md` §4), `tool_use` 의 입력을
`any` 로 풀었다가 다시 마샬하는 길은 R2.1 이 막은 그 모양이다. **조건을 다는
길만 파서의 코드를 한 줄도 안 바꾼다.**

### 2.3 파서가 고치지는 않는다

```text
   자르기는 마스킹이 아니다     앞에서부터 남기는 것이고 무엇을 가릴지의 규칙이 0 이다
   원래 깨진 것은 그대로        입력이 이미 잘못된 UTF-8 이면 고치지 않는다
   못 물리는 입력              앞이 전부 이어바이트이면 빈 문자열이 되고
                             Cut 이 전체 길이다.  멈추지 않는 경로가 0 이다
```

**`plain` 과 `raw` 는 안 잘린다** (FD R8.3). 그 `Text` 는 줄 바이트 그대로이고,
입력이 깨졌으면 깨진 채다 — **파서가 깨뜨린 것이 아니다.** 그 잔여는 5.3 이
U4 에 넘긴다.

### 2.4 자르는 자리가 하나다

```text
   파서가 자른다      internal/transcript 안의 한 자리
   화면은 안 자른다    U5 · U6 · U8 이 받은 Text 를 그대로 그린다
   왜               상한이 두 자리에 있으면 갈린다 (CONVENTIONS 1.4).
                    그리고 as=events 의 응답 크기가 파서에서 이미 묶여야
                    U4 가 N1 을 계산할 수 있다
```

## 4. `FuzzParse` — 「패닉 0」을 재는 자리 (Q3 = A)

**저장소에 퍼즈 시험이 0 이다** — 이 유닛이 첫 자리다.

### 4.1 대상은 하나다

```text
   퍼즈한다      Parse(b []byte, truncated bool)
                두 인자 다 Go 퍼즈가 바로 다루는 종류다 ([]byte · bool)

   안 만든다     FuzzParseLine · FuzzShell
                근거 — 코퍼스가 두 벌이 되고 (CONVENTIONS 1.4 의 결),
                ParseLine 은 Parse 가 지나는 경로라 같은 코퍼스가 이미 밟는다

   왕복은 표 시험이 진다    Shell 이 지은 바이트를 Parse 가 읽는 시험은
                         고정 입력이라야 뜻이 선다 (FD 8절).  퍼즈가 아니다
```

### 4.2 불변식 넷

| | 불변식 | 무엇을 지키나 |
|---|---|---|
| **F1** | **어떤 입력에도 패닉하지 않는다** | FD R10.2 · SECURITY-15. 패닉은 제어판과 Mediator 를 죽인다 |
| **F2** | **입력이 올바른 UTF-8 이면** `Cut > 0` 인 사건의 `Text` 도 올바른 UTF-8 이다 | Q1 = A 의 보장 (2.2). 응답의 조용한 손상을 막는다. **조건이 붙는 근거는 2.2.1 의 실측이다** — 퍼즈는 입력 바이트를 손에 들고 있어 `utf8.Valid(b)` 한 줄로 그 조건을 잰다 |
| **F3** | **줄을 안 버린다** — `Lines == (집계 줄 수) + (사건을 낸 줄 수)` | FD R1. 집계 줄 수는 `Elided != nil` 이면 1 이고, 사건을 낸 줄 수는 `Event.Line` 의 서로 다른 값의 수다 |
| **F4** | **`Head` 와 `Partial` 이 음수가 아니고 입력 길이를 안 넘는다** | 머리 · 꼬리 계산의 안전. 경계 산술이 도는 유일한 자리다 |

**F2 를 `Cut > 0` 으로 좁힌 것이 정확하다.** 상한이 걸리는 Kind 가 둘뿐이다
(2.2). `plain` 과 `raw` 의 `Text` 는 줄 바이트 그대로라 입력이 깨졌으면 깨진
채이고, **그것을 불변식에 넣으면 파서가 고치게 된다** — `constraints.md` §4 가
금지한 것이다.

**입력의 유효성과 무관한 자르기 불변식이 하나 더 있다** — `len(Text) + Cut` 이
원래 길이와 같고 음수가 아니다 (FD R8.2). 퍼즈가 F2 와 나란히 그것을 잰다.
**둘을 갈라 적는 이유는 조건이 다르기 때문이다** — F2 는 `utf8.Valid(b)` 안에서만
참이고 이쪽은 언제나 참이다.

### 4.3 시드 코퍼스

```text
   자리      internal/transcript/testdata/  (FD R15.1)
   내용      표 시험이 쓰는 픽스처 그대로.  f.Add 로 그것을 넣는다
   두 벌 0   같은 파일이 표 시험과 퍼즈 시드를 함께 먹인다 (FD R15.3)
   추가되는 것  퍼즈가 크래시를 찾으면 그 입력이 testdata/fuzz/FuzzParse/ 에
              파일로 쌓인다.  그때부터 시드라 회귀가 영원히 막힌다
```

**그 쌓임이 이 선택의 실제 기작이다** — 퍼즈의 값은 한 번 오래 도는 데 있지
않고, **찾은 것이 코퍼스가 되어 매 CI 에서 다시 도는 데** 있다.

### 4.4 CI 에서 어떻게 도나 — 값과 판단

**오늘 Go 의 거동을 값으로 적는다.**

```text
   go test ./internal/transcript          FuzzParse 의 시드만 한 번씩 돈다.
                                          변이(mutation)를 안 한다.  시간은 시드 수만큼
   go test -fuzz=FuzzParse -fuzztime=60s  실제 변이 퍼즈.  한 번에 대상 하나만 돈다
```

**그래서 오늘 CI 는 변이 퍼즈를 안 돌린다.** 스킵이 아니라 Go 의 기본 거동이고,
`.ci-allowed-skips` 의 스킵 상한 0 과도 무관하다 — 시드는 실제로 돈다.

**판단 — CI 에 `-fuzz` 를 붙이지 말 것을 권한다.**

```text
   붙이면   한 번에 대상 하나만 돌고 시간 상한을 줘야 한다.  무한히 도는 스텝은
           CI 의 성질을 바꾼다 — 이 저장소의 게이트는 전부 끝나는 명령이다
   안 붙이면 변이는 사람이 돌린다.  찾은 것은 코퍼스로 남아 CI 가 매번 다시 잰다
```

**사람이 집행하는 자리를 이름으로 적는다** — `internal/transcript` 를 고치는
커밋이 아래를 한 번 돌린다. **집행은 사람이고, 도는 스크립트가 없는 채로 기계
검사라고 적으면 그것이 거짓 초록이다** (`CLAUDE.md` 의 같은 결).

```text
   go test ./internal/transcript -run=XXX -fuzz=FuzzParse -fuzztime=60s
```

**`ci.yml` 은 이 유닛의 파일 행렬 밖이다.** CI 를 고칠지는 진행자에게 넘긴다
(6절 ④).

## 5. U4 에 넘기는 값 (Q2 = A)

**U1 은 사건 수 상한을 안 만든다.** 입력 상한이 출력을 지고, **U4 가 N1 을
지려면 아래 일곱이 있어야 한다** — 넘긴다고만 적으면 U4 가 다시 잰다.

### 5.1 증폭 — U4 가 받아야 하는 수

| | 값 | 근거 |
|---|---|---|
| 입력 상한 | 진행 파일 · `logs/` **10 MiB** (`MaxBlobBytes` 기본) · 링 **512 KiB** | `config.go:51`·`:100` · `record.go:64` · `transcript.go:28` |
| 최악의 줄 밀도 | 껍데기 줄 **21 바이트** (`{"type":"assistant"}` + 개행) | 그 줄이 사건 하나를 보증한다 (FD R5) |
| 최악의 사건 수 | 10 MiB / 21 = **약 499,000** | 위 둘의 나눗셈 |
| 사건 하나의 크기 | **224 바이트** (amd64 · 계산) | `Event` 의 필드 그대로. **벤치마크로 안 쟀다** — Code Generation 이 잰다 |
| 최악의 사건 배열 | **약 112 MB**. 슬라이스가 자라는 동안 잠깐 그 두 배 | 위 둘의 곱 |
| 파싱 비용 | 입력의 **약 2배** — 스캔 1x + 복사 1x | `decode.go:102-114` · `stream.go:272-278` |
| 제어판 경로 | 512 KiB / 21 = 약 25,000 사건 = **약 5.6 MB** | 문제가 아니다 |

**112 MB 는 본문이 아니라 구조체 개수에서 온다.** 2절의 상한이 도구 사건의
`Text` 를 200 · 500 바이트로 묶으므로 본문은 안 부푼다 — 부푸는 것은 **작은 줄이
많을 때의 `Event` 배열**이다.

### 5.2 줄이는 손잡이

```text
   from 으로 꼬리만 먹인다     GET log 가 이미 from 을 받는다.  폴링은 증분이라
                            전체 파싱이 첫 요청 한 번뿐이다
   동시성이 곱한다            요청마다 독립이다.  N 개가 동시에 오면 N 배다
   파서에는 손잡이가 없다      Q2 = A — Parse 는 상한 인자를 안 받는다
```

### 5.3 U4 가 함께 받아야 하는 잔여 하나 — 비UTF-8 원문 줄

**파서가 안 깨뜨려도 응답 형식이 바꾼다.**

```text
   경로   명령 단계가 이진 바이트를 stdout 에 뱉는다 (claim.go:633 이 링에 tee)
          -> 그 줄은 JSON 이 아니다 -> text · Sub = "plain" · Text 는 줄 바이트 그대로
          -> as=events 가 그것을 JSON 으로 인코딩한다
          -> encode.go:1040-1042 가 잘못된 바이트를 � 로 바꾼다

   그래서  as=events 의 답은 원문과 바이트가 같지 않을 수 있다.  오류는 안 난다
   막는 것  as=raw 와 제어판의 data 가 원문 그대로 나간다 (FD R8.5)
```

**U1 이 고치지 않는다** — 고치면 마스킹이다 (`constraints.md` §4). **`as=events`
가 바이트 동일을 보증하지 않는다는 것을 U4 가 자기 문서에 적어야 한다.**
`scene-gates.md` CB3 이 「봉인 뒤 tar 의 로그와 GET 의 답이 같은 바이트다」를
재는데, **그 게이트는 `as=raw` 로 재야 한다.**

## 6. 비-보안 NFR

**축을 넷만 세운다.** 확장과 가용은 안 세운다 — 이 패키지는 프로세스가 아니라
함수라 「늘린다」와 「멈춘다」의 대상이 0 이다 (계획 7절).

### 6.1 성능

```text
   파싱 비용        입력의 약 2배.  줄 길이에 선형이고 중첩 깊이에 안 비례한다
   시계를 안 받는다   같은 입력에 언제나 같은 값이다.  시험이 싸다
   목표 수치를 안 적는다   이 패키지가 도는 자리가 제어판(1초)과 Mediator(2초)이고
                       그 예산은 U5 · U4 의 것이다.  여기서 지어내지 않는다
```

### 6.2 자원

```text
   한 줄의 상한      입력 길이의 약 2배.  Q7 = A 가 그것을 선형으로 묶는다
   한 파일의 상한    사건 배열 약 112 MB (5.1).  U4 가 진다
   여는 자원        0 — 파일 · 소켓 · 고루틴 · 타이머를 안 만든다
   막는 것이 없는 자리  한 줄의 길이.  저장소에 줄 길이 상한이 0 이다 (계획 1.2).
                     파일 상한이 그것을 간접으로 묶는다 — 한 줄이 파일보다 길 수 없다
```

### 6.3 신뢰

```text
   실패 등급        0.  error 를 안 돌려준다 (R10.1)
   패닉             0 이어야 한다 (R10.2).  F1 이 잰다
   못 읽은 줄        버리지 않는다.  text/plain 또는 raw 로 남는다 (R3.1 · R3.2)
   닫히는 쪽으로 실패  못 읽음이 접근을 열지 않는다.  원문을 그대로 보인다
```

### 6.4 유지보수

```text
   커버리지         패키지별 80%.  게이트가 프로파일에서 패키지를 뽑으므로
                   새 패키지가 파일 한 줄 안 고쳐도 자동으로 걸린다 (계획 1.5)
   예산             FD 14절이 쟀다 — 63/65 = 96.9% 에서 시작한다.  다시 안 잰다
   하한을 못 올린다   .coverage-contract.yml 에 패키지별 하한 장치가 없고
                   그 파일은 주인이 따로다.  안 만진다
   두 벌 금지        SplitLines · String · Bool · Int 를 transcript 가 혼자 진다 (R11)
```
