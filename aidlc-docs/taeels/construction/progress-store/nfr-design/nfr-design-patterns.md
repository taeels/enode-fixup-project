# U3 `progress-store` — NFR 설계 (패턴)

규칙 Step 6 의 산출물 둘 중 첫째다. 둘째는 `logical-components.md`.

**값은 여기서 안 정한다.** 형식은 Functional Design 이 (R1 ~ R36), 숫자는 NFR
Requirements 가 (V1 ~ V6 · R37 ~ R42) 이미 닫았다. **이 단계가 짓는 것은 그
값들이 어떤 순서로 서고 무엇이 그것을 지키는가**다.

규칙 번호는 이어 쓴다 — FD 가 R1 ~ R36, NFR Requirements 가 R37 ~ R42,
**이 문서가 R43 ~ R50** 이다.

---

## 0. 패턴 다섯 중 이 유닛이 지는 것은 둘이다

`execution-plan.md` 의 NFR Design 절이 회차 전체의 패턴 다섯을 적었다.
**유닛마다 지는 것이 다르므로 갈라 적는다 — 안 적으면 다음 사람이 빠뜨린 것으로
읽는다.**

| | 패턴 | 지는 유닛 | 이 문서 |
|---|---|---|---|
| ① | 총 길이 상한에 닿았을 때의 거동 — **찍는 쪽** | **U3** | **1절** |
| ① | 같은 거동이 **보이는 자리** — 응답 헤더와 화면 | **U4** (`X-Enode-Log-Capped`) · **U5** · **U8** | **안 짓는다** |
| ② | 청크 PUT 실패가 실행과 링을 안 막는 분리 | **U7** | **안 짓는다** |
| ③ | 폴링 타이머의 분리 — 목록 5초 · 단계 카드 2초 | **U8** | **안 짓는다** |
| ④ | 파서가 아는 키만 읽는 규율 (SECURITY-13) | **U1** | **안 짓는다** |
| ⑤ | 봉인 때의 순서 — 진행 파일이 먼저다 (D1) | **U3** | **2절** |

### 0.1 안 짓는 넷을 이름으로 적는 이유

```text
   ① 의 보이는 쪽   U3 은 Progress.Capped 를 내는 데서 끝난다 (R46).
                   헤더 이름도 화면 문장도 U3 의 것이 아니다

   ②              업로더는 internal/enode 에 산다.  record 는 그 실패를 모른다 —
                   U3 은 들어온 청크만 다룬다

   ③              타이머는 브라우저에 있다.  이 유닛은 화면을 0 줄 만진다

   ④              파서는 internal/transcript 에 산다.  U3 은 바이트를 다루고
                   내용을 안 판다.  **표시 줄을 찍기만 하고 읽지 않는다**
```

**넷 다 「이 유닛이 안 한다」이지 「아무도 안 한다」가 아니다.**

## 1. 패턴 ① — 상한에 닿는 순간

형식은 FD 가 닫았다 (R11 자르는 자리 · R12 표시 줄 한 번 · R13 `Total` 은 파일
크기 · R14 `Capped` 의 근거 · R15 닿은 뒤 안 쓴다). **여기서 닫는 것은 그 다섯이
실제로 어떤 차례로 서고 중간에 죽으면 무엇이 남는가**다.

### 1.1 닿는 순간의 순서

락 안이다 (R28). 쓰기가 **둘**이고 그 앞에 개행 보장이 하나 붙는다.

```text
   ①  예산을 잰다        budget = limit - 지금 파일 크기
   ②  자를 자리를 찾는다   청크 안에서 budget 을 안 넘는 마지막 개행     R11
   ③  [쓰기 W1]         그 자리까지 쓴다.  **0 바이트일 수 있다**
   ④  개행을 보장한다     파일의 마지막 바이트가 개행이 아니면 개행 하나   **R43**
   ⑤  [쓰기 W2]         표시 줄 + 개행을 **한 번의 쓰기로**            **R44**
   ⑥  Total 을 잰다      파일 크기.  표시 줄이 든다                    R13
   ⑦  Capped = true     근거는 마지막 줄이지 크기가 아니다             R14
```

### 1.2 ④ 가 왜 있나 — 없으면 표시 줄이 스스로를 망친다

**도는 동안 진행 파일의 꼬리는 반쪽 줄인 것이 정상이다.** 청크 경계가 줄 경계가
아니기 때문이다 (`domain-entities.md` 2.4). 그리고 ③ 이 0 바이트를 쓰는 경우
(예산 안에 개행이 없다 · R11) 그 반쪽 줄이 **그대로 꼬리로 남는다.**

```text
   ④ 가 없으면   {"type":"assis  +  {"type":"enode.capped","bytes":N}\n
                 -> 한 줄이 되고 **파싱이 안 된다**
                 -> R14 의 「마지막 줄이 표시 줄인가」가 거짓
                 -> Capped 가 영영 참이 안 되고 **표시 줄이 무한히 쌓인다**

   ④ 가 있으면   {"type":"assis\n  +  {"type":"enode.capped","bytes":N}\n
                 -> 반쪽은 **자기 줄**로 끝나고 U1 의 파서가 raw 하나로 올린다
                 -> 표시 줄이 온전히 마지막 줄이 된다 -> Capped = true
```

**개행 하나가 무한 루프와 사건 하나를 가른다.** 그 한 바이트도 `Total` 에 든다
(R13 의 예외가 0 이다).

### 1.3 중간에 죽으면 무엇이 남나 — **네 틈 전부 수렴한다**

| 죽는 틈 | 파일에 남는 것 | 다음 호출이 보는 것 | 수렴 |
|---|---|---|---|
| ③ 앞 | 상한 이하 · 표시 줄 없음 | `Capped` 거짓 | 같은 판정을 다시 해서 ③ ~ ⑤ 를 돈다 |
| ③ 과 ④ 사이 | 잘린 자리까지 · 표시 줄 없음 | `Capped` 거짓 | 예산이 0 이라 ③ 이 0 바이트, ④ ⑤ 를 돈다 |
| ⑤ 중간 (표시 줄이 반쪽) | 끝나지 않은 조각 하나 | `Capped` 거짓 | **④ 가 그 조각을 개행으로 닫고** ⑤ 가 온전한 줄을 박는다 |
| ⑤ 뒤 | 정상 | `Capped` 참 | R15 로 더 안 쓴다 |

**넷 다 「표시 줄이 온전히 마지막 줄」로 끝난다.** 상태가 전부 디스크에 있어
(파일 이름이 시도 · 마지막 줄이 `Capped`) 메모리에 이어받을 것이 0 이기 때문이다.

**대가 하나** — 셋째 줄에서 크래시 한 번에 깨진 조각이 하나 남는다. 화면에
`raw` 사건 하나로 뜬다. **관측의 잡음이지 손실이 아니다** (1.6).

### 1.4 「정확히 한 번」(R12)이 서는 축 셋

```text
   동시 쓰기    (run, seq, name) 뮤텍스가 ① ~ ⑦ 을 감싼다 (R28).
               둘이 동시에 ⑤ 를 돌 수 없다

   재시도       시도마다 **파일이 다르다** (R2 · R9).  Capped 가 파일마다이고
               새 시도는 0 부터 다시 센다.  앞 시도 파일은 R9 가 지운다

   재시작       **메모리에 든 상태가 0 이다.**  Capped 는 파일의 마지막 줄에서,
               시도는 파일 이름에서 읽는다.  프로세스가 죽었다 살아나도
               같은 답이 나온다 — 1.3 의 표가 그 위에서 성립한다
```

**셋째가 이 설계의 값이다.** 상태를 메모리에 두면 재시작이 셋째 열을 무너뜨린다.

### 1.5 `Total > limit` 이 정상이라는 것을 무엇이 보장하나

R13 이 `Total` 을 「파일의 크기」 하나로 정의했고 표시 줄과 R43 의 개행이 거기
든다. **그래서 닿은 뒤에는 `Total` 이 상한을 넘는다 — 그것이 정상이다.**

```text
   보장하는 것 셋
     정의     Total 의 뜻이 하나다.  예외가 0 이라 「어떤 Total 은 다르다」가 없다
     금지     크기를 상한과 견주어 Capped 를 판정하지 않는다 (R14)
     시험     **Total > limit 을 정상으로 못박는 시험을 둔다** (R45).
              그 시험이 없으면 다음 사람이 assert Total <= limit 을 쓴다

   넘어가는 근거 하나 더   같은 저장소의 WriteBlob 이 limit+1 을 읽어 초과를 가른다
                        (record.go:287).  **넘었음을 알려면 넘겨야 한다**
```

**이상으로 읽힐 수 있는 자리 셋을 이름으로 적는다.**

| 자리 | 위험 | 오늘 왜 안 나나 |
|---|---|---|
| U4 의 헤더 | `X-Enode-Log-Capped` 를 `Total >= limit` 로 짜면 틀린다 | `Progress.Capped` 가 이미 값으로 오므로 견줄 이유가 없다. **경계 문서가 그것을 적는다** (R46) |
| U7 의 오프셋 | `Total` 을 다음 `from` 으로 쓰다 상한을 넘은 값을 이상으로 읽는다 | `Capped` 가 참이면 노드가 **더 안 올린다** (FR-5). `Total` 을 다시 안 쓴다 |
| 시험 | `Total <= limit` 을 불변식으로 적는다 | **R45 가 반대 방향으로 못박는다** |

### 1.6 ① 이 못 막는 것

```text
   U4 · U7 이 각자 크기 비교를 넣는 것   **코드로 못 막는다.**  문서(R46)와
                                      시험(R45)으로만 막는다.  경계 밖이다

   크래시가 남긴 조각 하나              막지 않는다.  raw 사건 하나로 뜬다.
                                      크래시 한 번에 조각 하나이고 무한이 아니다

   파일을 밖에서 손으로 고치는 것        범위 밖.  0600 이 프로세스 밖의 쓰기를 막지만
                                      같은 사용자의 손은 안 막는다

   상한 자체가 낮은 것                  값은 MaxBlobBytes 이고 decisions.md 2절이
                                      「새 상한을 안 만든다」로 닫았다
```

### 1.7 경계 — U3 이 어디서 끝나나

```text
   U3 이 진다      진행 파일에 무엇을 어떤 순서로 쓰나.
                  Progress{Total, Attempt, Capped} 를 짓는 것까지

   여기서 끝난다    **Progress 를 반환하는 순간**                        R46

   U4 가 받는다    Capped -> X-Enode-Log-Capped.  헤더 이름은 U4 의 것
   U5 · U8 이 그린다  NC-4 의 문장.  「멈췄다」와 「끝났다」를 가르는 한 줄
   U1 이 읽는다     표시 줄을 Kind 로.  **U3 은 찍기만 하고 안 읽는다**
```

## 2. 패턴 ⑤ — 봉인 때의 순서

### 2.1 재앙의 기제는 tar 가 아니라 **chmod** 다 — 실측으로 교정한다

`execution-plan.md` 가 이 패턴을 「**진행 파일을 지우는 것이 tar 보다 앞이다**」로
적었다. **코드를 읽으면 tar 는 그 자리에 없다.**

```text
   Seal 이 하는 것   manifest · steps · verdict 를 쓰고 .tmp-* 를 걷고
                    **seal(d) 로 끝난다** (record.go:120).  tar 를 안 짓는다

   seal(d) 가 하는 것  Walk 으로 파일 전부 0444 · 디렉터리 전부 0555
                    (record.go:174 · :180).  **여기서 되돌릴 수 없게 된다**

   Tar 는 언제        **GET /v1/runs/{id}/record 때다.**  호출자가 하나뿐이고
                    (api.go:1043) Sealed() 게이트 뒤라 (api.go:1037 의 409)
                    봉인보다 한참 뒤에 아무 때나 돈다
```

**그러므로 순서가 지켜야 하는 것은 `seal(d)` 의 chmod 다.** tar 는 그 아래쪽이고,
chmod 를 지난 시점에 이미 늦었다. 「tar 보다 앞」은 결과적으로 참이지만
**막아야 할 것을 가리키지 않는다** — 5절이 이 문장을 고칠 후보로 넘긴다.

### 2.2 순서와 그 자리

```text
   func Seal(...) {
       DropProgress(runID)          <- **여기다.**  실패해도 안 멈춘다      R47 · R48
       if Sealed(runID) { return }  <- 조기 반환보다도 앞이다 (FD 의 R22)
       Open(runID)
       ... manifest · steps · verdict ...
       ... blobs 의 .tmp-* 를 걷는다 ...   record.go:112
       return seal(d)               <- **chmod.  여기를 지나면 못 되돌린다**
   }
```

**집 안에 선례가 있다** — `.tmp-*` 를 걷는 줄이 `seal(d)` 바로 앞에 있다
(`record.go:112` ~ `:119`). 「굳히기 전에 걷는다」가 이 함수의 기존 결이고
`DropProgress` 가 같은 자리에 선다.

**다만 `DropProgress` 가 그보다 더 앞이다.** 이유가 하나 더 있기 때문이다.

```text
   .tmp-*      쓰기가 다 끝난 뒤에 걷어야 한다.  그래서 끝이다
   DropProgress  **이미 봉인된 Run 에 다시 불려도 걷어야 한다.**  늦은 청크가
                만든 고아 트리가 그 자리다 (2.6).  조기 반환 뒤에 두면 못 걷는다
```

### 2.3 순서가 깨지면 무엇이 일어나나 — **오늘은 아무 일도 안 난다**

**두 겹이기 때문이다.** 그리고 **바닥은 순서가 아니라 자리다.**

| | 겹 | 무엇 | 깨지면 |
|---|---|---|---|
| 1 | **순서** | `DropProgress` 가 chmod 보다 앞 | 진행 트리가 남는다. **지울 수는 있다** |
| 2 | **자리** | 진행 트리가 `seal` 의 `Walk` 밖 (D1 · R35 · R36) | **여기가 바닥이다** |

```text
   오늘 (D1 이 있다)        순서를 놓쳐도 진행 트리는 Walk 밖이라 0444 가 안 된다.
                          지울 수 있고 N2 의 쓸기가 60초 안에 걷는다 (V1 · V3).
                          **재앙 0**

   D1 이 없었다면 (트리가   chmod 가 0444 · 0555 로 굳힌다.  unseal 은 제품 경로에
   run-<id>/ 안이었다면)    없고 테스트 정리 전용이다 (record.go:187 의 주석).
                          -> **원문이 아무도 못 지우는 상태로 영구가 된다**
                          -> 그리고 tar 에 실려 **봉인 묶음이 원문을 담는다** —
                             질문 1 = B 가 산 것이 그 자리에서 무너진다
```

**그래서 순서는 값싼 겹이고 자리가 안전장치다.** `application-design.md` 4절이
「순서는 값이고 자리는 안전장치다. 둘을 함께 둔다」로 적은 것이 이 자리다.

### 2.4 지우기가 실패하면 — **봉인을 계속 짓는다**

| | 고른 것 | 대가 |
|---|---|---|
| **R48** | `DropProgress` 가 실패해도 `Seal` 은 계속 간다. 오류를 로그로 내고 삼킨다 | 진행 트리가 남는다. **N2 의 쓸기가 받는다** — Run 이 종료 상태이므로 V3 의 조건 ① 에 걸려 ≤ 60초에 걷힌다 |
| | (안 고른 것) 멈춘다 | **봉인이 안 된다.** `I4` 가 안 서고 Record 가 안 생긴다. 관측 표면의 실패가 기록을 막는 것이고 `application-design.md` 2.1 이 금지한 자리다 |

**근거는 실패 등급이다** (R25 — 진행 파일의 쓰기 · 걷기 · 드롭이 전부 보조).
**보조가 치명을 막으면 등급이 뒤집힌 것이다.**

### 2.5 안전장치가 깨지는 길 셋과 그것을 재는 시험

| | 깨지는 길 | 재는 시험 |
|---|---|---|
| 1 | 누가 진행 트리를 `<Root>/run-<id>/` 안으로 옮긴다 | **R35** — 진행 파일을 쓴 Run 을 봉인하고 tar 를 풀면 `progress/` 항목이 **0 개**다 |
| 2 | `seal()` 의 `Walk` 대상이 `s.dir(runID)` 에서 `s.Root` 로 바뀐다 | **R36** — 봉인 뒤에도 진행 트리를 **지울 수 있다** (쓰기 비트가 살아 있다) |
| 3 | 심볼릭 링크로 트리가 `Walk` 안에 나타난다 | `filepath.Walk` 은 `lstat` 기반이라 링크를 안 따라간다 — 링크 파일 자체만 굳는다. **R35 가 그 항목을 tar 에서 잡는다** |

**셋 다 시험이 직접 잰다.** 규칙으로만 적으면 다음 사람이 1 번 길로 간다.

### 2.6 ⑤ 가 못 막는 것 — 늦은 청크의 고아 트리

FD 5.1 이 t0 ~ t4 로 적은 창이다. `putLog` 가 DB 의 `run.State` 로 410 을 내고
`Sealed()` 를 안 보기 때문에 생긴다 (`api.go:879`).

```text
   t0   PUT 이 run.State 검사를 지난다.  아직 RUNNING 이다
   t1   Run 이 종료 상태가 되고 sealRecord 가 돈다
   t2   Seal 이 DropProgress 로 트리를 지운다
   t3   t0 의 PUT 이 닿는다.  **트리가 다시 생긴다**
   t4   Seal 이 다시 안 불리면 그대로 남는다
```

**⑤ 가 막는 것** — `Seal` 이 **다시 불리면** 걷는다. R47 이 조기 반환보다 앞이라
이미 봉인된 Run 에도 돈다.

**⑤ 가 못 막는 것** — `Seal` 이 다시 안 불리는 경우. **N2 가 그것을 받는다.**

```text
   받는 자리   NFR Requirements 의 V3 조건 ① — Run 이 종료 상태(또는 DB 에 없다)
```

## 3. 규칙 — R43 ~ R50

| | 규칙 | 근거 |
|---|---|---|
| **R43** | 표시 줄을 쓰기 전에 **파일이 개행으로 끝나는 것을 보장한다.** 아니면 개행 하나를 먼저 쓴다 | 1.2. 없으면 반쪽 줄이 표시 줄과 붙어 파싱이 깨지고 **표시 줄이 무한히 쌓인다** |
| **R44** | 표시 줄과 그 개행을 **한 번의 쓰기로** 낸다. 버퍼를 나누지 않는다 | 1.3. 나누면 크래시가 남기는 조각이 는다 |
| **R45** | **`Total > limit` 은 정상이다.** 시험이 그것을 못박는다 — `Total <= limit` 을 불변식으로 적지 않는다 | 1.5. R13 의 정의가 하나이고 표시 줄과 R43 의 개행이 거기 든다 |
| **R46** | U3 의 경계는 **`Progress` 를 반환하는 순간** 끝난다. 헤더 이름 · 화면 문장 · `Kind` 는 U3 의 것이 아니다 | 1.7. 경계를 안 적으면 U4 가 크기 비교를 자기 손으로 짠다 |
| **R47** | `DropProgress` 는 **`seal(d)` 의 chmod 보다 앞이고 조기 반환보다도 앞**이다 | 2.1 · 2.2. chmod 가 되돌릴 수 없게 만드는 자리다. 조기 반환 앞인 것은 고아 트리 때문이다 |
| **R48** | `DropProgress` 가 실패해도 **봉인을 계속 짓는다** | 2.4. 보조가 치명을 막으면 등급이 뒤집힌 것이다 (R25) |
| **R49** | 안전장치는 **두 겹이고 바닥은 자리**다 — 순서(R47)가 깨져도 자리(D1 · R35 · R36)가 재앙을 막는다 | 2.3. 순서 하나에 기대면 한 번의 실수가 원문을 영구로 만든다 |
| **R50** | ⑤ 가 못 막는 고아 트리를 **N2 의 V3 조건 ① 이 ≤ 60초에 받는다** | 2.6. 두 값이 한 결함을 전이와 주기로 나눠 받는다 |

## 4. 물음 — **0 이다**

규칙 Step 3 이 범주 다섯을 전부 보라고 한다. **전부 평가했고 진짜 갈림이
0 이라 억지로 만들지 않았다.**

| 범주 | 이 유닛에서 | 왜 안 묻나 |
|---|---|---|
| Resilience | 실패 등급 · 크래시 수렴 · 봉인 때의 실패 | **값이 이미 닫혔다** — R25 가 등급을, R48 이 봉인 때를 정했다. 1.3 의 수렴은 **고르는 것이 아니라 도출**이다 (상태가 전부 디스크에 있으므로 수렴한다) |
| Scalability | 디스크 봉투 · 쓸기 주기 | NFR Requirements 4.2 와 V1 이 값으로 닫았다. **이 단계가 새로 고를 값이 0** |
| Performance | 쓰기 경로 | 로컬 파일 append 하나다. 청크 주기 · 폴링은 다른 유닛의 것이고 값이 닫혔다 |
| Security | 노출 기간 · 권한 · 봉인 무결성 | V5 = 6시간 · R4 = 0600 · R35 · R36 이 전부 값이다. **SECURITY 판정도 이미 났다** (`nfr-requirements.md` 6절 · 차단 findings 0) |
| Logical Components | 큐 · 캐시 · 서킷브레이커 | **구성요소가 0 이다.** 근거는 `logical-components.md` |

**갈림이 있었으면 멈추고 물었다.** 앞선 두 단계가 그 자리를 이미 지났다 —
Functional Design 에서 물음 열하나, NFR Requirements 에서 넷. **이 단계가 하는
일은 그 답들이 어떤 순서로 서는지를 적는 것이고 새 값이 0 이다.**
