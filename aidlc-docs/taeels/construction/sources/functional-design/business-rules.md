# U4 `sources` — 필터와 우선순위와 거절

규칙마다 **어긴 것이 실제로 거절되는가**를 잴 수 있는 형태로 적는다 — 문장 하나에
거절 사유 하나다. 형식은 `domain-entities.md`, 지나가는 길은
`business-logic-model.md`.

**에러 문자열과 로그는 영어다** (`CONVENTIONS.md` 2.1). 주석과 이 문서는 한국어다.

---

## 1. 요청 필터 — 계약이 적은 이름만 열린다

```text
   R1   agent.mcp 가 이름을 적은 서버만 허용목록에 실린다.  출처가 어디든 같다
        (decisions.md 6절 ⑥ — 팩은 정의의 출처이지 허가의 출처가 아니다)
   R2   agent.mcp 가 비면 허용목록이 빈다.  {"mcpServers":{}} 이고 {} 가 아니다
        (U1 이 이미 짓는다).  이때는 워크스페이스 파일을 아예 안 연다
```

**R1 이 이 유닛의 뼈대다.** 출처가 느는 것은 **선택지가 느는 것이지 권한이 느는
것이 아니다** — U5 의 팩도 같은 필터를 탄다.

요청 이름의 모양은 여기서 다시 안 본다 — U2 의 `checkComponentTypes` 가 배열인지와
원소가 빈 문자열이 아닌지를 보고 **제출에서 400** 이다. 같은 이름을 두 번 적은
계약은 거절하지 않는다. 이름의 집합이 같으므로 결과가 같다.

---

## 2. 우선순위 — 노드가 워크스페이스를 이긴다

```text
   R3   같은 이름이 노드 선언과 워크스페이스에 둘 다 있으면 노드 것을 쓴다.
        Note 를 남긴다
        mcp server %s is declared by both the node and the workspace;
        the node declaration wins
```

값은 `features.md` 3.2 와 `decisions.md` 2절이 이미 닫았다 — 여기서 다시 안 정한다.
**그 값이 지키는 것**은 이것이다: 저장소에 쓰는 사람이 노드 소유자가 선언한 이름을
가로채지 못한다. 계약이 `requires: mcp.<이름>` 으로 소유자의 선언을 보고 노드를
고른 뒤, 저장소의 `.mcp.json` 이 그 이름의 실행 경로를 바꿔치는 길이 닫힌다 —
팩에 대해 `decisions.md` 6절 ⑦ 이 거절로 막은 것과 같은 위협이다.

**팩과 달리 거절이 아니라 무시인 이유** — 워크스페이스 파일은 계약이 실어 보낸 것이
아니라 저장소에 원래 있는 것이다. 저장소가 자기 개발용으로 같은 이름을 쓰는 것은
흔하고, 그것을 단계 실패로 만들면 MCP 와 무관한 이유로 함대가 멈춘다.

---

## 3. 없는 이름은 하네스를 안 띄운다

```text
   R4   요청한 이름이 노드에도 워크스페이스에도 없으면 단계를 실패로 보고한다.
        하네스를 안 띄운다
        mcp server %s is not available on this node
   R5   없는 이름이 여럿이면 정렬한 순서의 첫 이름으로 거절하고,
        나머지는 같은 문장으로 Note 에 남긴다 (답 6=A)
```

문구는 팩이 박은 그대로다 (`features.md` 3.2 · `scene-gates.md` CA4). **게이트가
그것을 부분 문자열로 찾으므로 이름 하나짜리 단수형을 유지한다.**

**조용히 빼지 않는 것이 이 규칙의 값이다** (`ADR-035` §3). 빼고 돌면 하네스가
`exit 0` 으로 끝나고 성공이 봉인된다 — 단계는 초록인데 모델은 그 도구를 못 봤다.

거절은 `HarnessResult{Reason: ReasonError, Message: ...}` 로 간다. **새 `Reason`
을 안 만든다** — `runner.go` 의 ② 가 이미 그 꼴로 돌려주고
`claim.go:784` 가 `res.Error` 에 `harness: error <문구>` 로 싣는다.

---

## 4. 워크스페이스를 읽는 조건

```text
   R6   Local.Workspace 가 빈 문자열이면 워크스페이스 출처가 없다.
        파일을 안 읽는다
```

`claim.go:558` 이 워크스페이스가 없을 때 `dir` 을 `os.TempDir()` 로 떨어뜨린다.
거기의 `.mcp.json` 을 읽으면 **아무나 쓸 수 있는 디렉터리의 파일이 이 노드의
허용목록 출처가 된다.** 워크스페이스가 없는 노드는 출처도 없다.

---

## 5. 못 읽는 파일은 요청이 있을 때만 만난다

```text
   R7   .mcp.json 을 읽거나 풀지 못하면 단계를 실패로 보고한다
        cannot read workspace .mcp.json: %v
```

**답 1=A 와 4=A 가 만나 규칙이 하나로 줄었다.** 4=A 는 「요청이 있을 때만
치명」인데, 1=A 가 **요청이 0 이면 파일을 아예 안 열게** 한다 (R2). 그래서
「요청이 0 인데 파일이 깨진」 경우가 구조적으로 안 생긴다 — 조건문이 아니라
호출 자리가 그것을 보장한다.

```text
   없는 파일                 빈 것이다.  오류가 아니다
   mcpServers 키가 없는 파일   빈 것이다.  오류가 아니다
   JSON 이 아니거나 종류가 틀린 파일   R7
   읽기 권한이 없는 파일        R7
```

**문구에 파일 경로를 안 싣는다.** 그 문구는 `res.Error` 로 봉인에 들어가고,
노드의 디렉터리 구조는 계약 작성자가 알 것이 아니다. 파일은 하나뿐이라 이름으로
충분하다.

**대가를 적어 둔다** — 요청한 이름이 전부 노드 선언에 있어도, 그 저장소의
`.mcp.json` 이 깨져 있으면 단계가 죽는다. 읽는 시점이 이름을 고르기 전이기
때문이다. 그 대신 얻는 것은 진단의 정확함이다: 깨진 파일과 오타가 다른 문구로
나온다 (R7 대 R4).

## 6. 워크스페이스 항목의 모양

```text
   R8   요청된 워크스페이스 항목에 command 도 url 도 없으면 단계를 실패로 보고한다
        workspace mcp server %s declares neither command nor url
```

**요청된 것만 본다.** 저장소가 자기 사정으로 적어 둔 다른 항목은 이 단계와 상관이
없다. 노드 선언에는 이 규칙이 필요 없다 — U3 의 `validateMCP` 가 같은 모양을
설정 시점에 이미 거절하고, 그때는 노드가 안 뜬다.

**왜 거절인가** — 종류를 못 정하는 항목은 `type` 을 채울 수 없고 (7절), 채우지
못한 항목은 하네스가 **말없이 버린다** (계획 1.3). 계약이 이름으로 요청한 것이
조용히 사라지는 것은 R4 가 막으려는 바로 그 실패다.

**검사 순서** — 이름 순으로 돌면서 만나는 자리에서 거절한다. 그래서 R8 과 R4 가
함께 걸린 계약은 **이름 순으로 앞선 것**의 문구를 받는다. 같은 계약이면 같은
문구가 나온다 (`ADR-014` 결정 3 의 결).

## 7. `type` 은 없을 때만 채운다

```text
   R9   허용목록 항목에 type 이 없으면 채운다 —
        command 가 있으면 "stdio", url 이 있으면 "http".
        이미 있으면 손대지 않는다
```

계획 1.3 의 실측이 근거다. `type` 도 `command` 도 없는 항목은 `mcp_servers`
목록에서 빠진다 — `failed` 로도 안 나타난다.

```text
   막는 것    url 만 적힌 항목이 조용히 사라지는 것.
             ADR-035 §4.4 의 예시가 오늘 그 모양이다
   못 막는 것  종류가 틀린 것.  sse 서버를 url 만으로 적으면 http 로 채워지고
             그 서버는 failed 로 나타난다.  침묵이 아니라 실패라서 사람이 본다
```

**이미 있으면 안 덮는 것**이 규칙의 절반이다. 소유자가 `type: sse` 를 적었거나
저장소가 `type: http` 를 적었으면 그것이 이긴다 — 우리는 비어 있는 자리만 채운다.

## 8. Notes 는 이름만 담는다

```text
   R10   Notes 에 값을 안 담는다.  서버 이름 · 출처 · 무엇을 했는가만 담는다
```

담는 사실 넷이다.

```text
   겹쳤다        R3 의 문장
   없다          R5 의 나머지 이름들
   요청 안 했다   워크스페이스가 선언했으나 이 단계가 요청하지 않은 이름
                workspace .mcp.json declares %s, which this step did not request
   (U5 가 더한다)  팩이 실었으나 요청 안 한 이름 — 같은 자리 같은 꼴이다
```

**Notes 는 노드 로그로 나간다** (답 5=A). `runHarness` 가 resolve 뒤에 한 줄씩
`Info` 로 찍는다 — 단계마다 한 번이고 광고 주기와 무관하다. `Job.Log` 가 nil
이면 안 찍고, 그때도 판정은 같다.

```text
   R11   거절로 끝날 때도 Notes 를 채워 돌려준다.  로그를 먼저 찍고 실패를 낸다
```

U1 이 「보조 실패에도 이미 얻은 플래그를 돌려준다」로 세운 결과 같다 — **왜
실패했는지를 아는 데 필요한 사실이 실패와 함께 사라지면 안 된다.**

`logs/` 에는 안 싣는다. `selectLogs` 의 허용목록이 전문 셋뿐이고 게이트
CA1 · CA4 · CA5 가 그 파일을 `head -1` 로 읽는다 (계획 1.6).

## 10. 이 규칙들이 못 잡는 것

다음 사람이 「검증됐다」로 읽지 않게 이름으로 적는다.

```text
   못 잡는다   워크스페이스 서버가 실제로 뜨는가
              mcpUp 은 노드 선언에만 쓴다.  안 뜨면 init 줄에 failed 로 나온다

   못 잡는다   원격 선언만으로 원격 MCP 가 도는가 (답 7=A)
              인증이 헤더로 가는데 credential 은 파일에 안 나간다.  소유자가
              headers 를 Extra 로 적어야 돈다 — 그 사실이 오늘 어디에도 안 적혀 있고
              이 유닛이 decisions.md 로 올린다

   못 잡는다   저장소가 env 에 값을 평문으로 적은 것
              원문 그대로 옮기므로 그 값이 계장 디렉터리의 파일에 실린다.
              우리가 만든 노출이 아니다 — 저장소에 이미 평문으로 있고,
              그 파일은 단계 끝에 계장 디렉터리와 함께 지워진다

   못 잡는다   저장소가 새 이름을 심는 것
              R3 이 막는 것은 노드 선언 이름의 가로채기뿐이다.  새 이름은
              계약이 R1 로 요청해야만 열리므로 저장소와 계약 둘 다가 필요하다.
              그것이 features.md 3.4 가 의도한 경로다
```
