```text

   계획    ../../plans/panel-past-functional-design-plan.md
   답      1=A · 2=A · 3=A · 4=A · 5=A · 6=A
   기준선   b3c7a24
```

**흐름이 하나다** — 사람이 지난 작업에서 Run 하나를 누르면 무슨 일이 도나.
폴링이 없고 타이머가 없다. 그래서 이 문서는 그 한 번을 적는다.

---

## 1. 한 번 누르면 — 제어판 쪽

답 5 = A. **브라우저는 요청 하나이고 모으는 일을 제어판이 한다.**

```text
   ①  GET /api/record?run=<id>          브라우저 -> 제어판.  오늘 그대로다
   ②  Client.Status(run)                제어판 -> Mediator.  단계 목록
   ③  단계마다
         StepLog(run, seq, step.ID, "events")
         StepLog(run, seq, step.ID, "raw")
   ④  봉투 하나로 묶어 낸다 (domain-entities 3절)
```

**브라우저의 계약이 안 바뀐다.** 오늘도 `/api/record` 한 번이었고 tar 하나가
전부를 들고 왔다. **바뀌는 것은 제어판 안쪽이다.**

```text
   왜 제어판이 모으나   브라우저가 N+1 을 지면 실패 갈래가 N+1 개 생긴다.
                    단계 셋 중 하나만 실패한 화면을 사람이 읽을 방법이 없다
   왜 폴링이 아닌가    봉인된 것은 안 자란다.  도는 것은 위의 카드가 이미 그린다 (U5)
```

### 1.1 요청 수의 천장

```text
   지금    1    tar 하나
   뒤     1 + N  단계 수만큼.  3단계면 4 · 20단계면 21
   언제    **누를 때만.**  자동 갱신이 0 이라 초당 요청이 0 이다
```

**「한 번 읽고 끝」은 「누를 때마다 한 번」이다.** 다시 누르면 다시 읽는다 —
영원히 한 번이 아니다. 봉인 전 Run 을 눌렀다면 그 사이에 내용이 자라 있다.

## 2. 봉인 전과 뒤의 갈림

답 3 = A. **갈림을 제어판이 안 만든다** — `GET log` 가 이미 갈라서 답한다.

```text
   Run 이 안 끝났다    steps[].source 가 progress.  화면에 「봉인 전」
   Run 이 끝났다      steps[].source 가 sealed.  그대로 읽는다
```

**제어판이 하는 일은 헤더를 봉투에 옮겨 싣는 것뿐이다.** 어느 쪽인지를 판정하는
코드가 0 이다 — 판정은 U4 의 `logSliceOf` 가 이미 했다.

### 2.1 두 신호가 같은 답을 내야 한다

```text
   첫째   source == "sealed"
   둘째   transcript.elided 가 있다 (걷는 일은 봉인 때 일어난다)
```

**둘이 어긋나면 하나가 틀린 것이다.** 어긋나는 모양은 둘뿐이다.

```text
   sealed 인데 elided 가 없다      그 단계가 아무것도 안 걷혔다 — 정상이다
                                (명령 단계는 도구 결과가 0 이라 걷을 것이 없다)
   progress 인데 elided 가 있다    **정상이 아니다.**  진행 파일에 봉인 표시가 섞였다
```

**그래서 불변식은 한 방향이다** — `progress` 면 `elided` 가 없다.
`business-rules` 가 그 방향으로 적는다.

## 3. 총 길이 0 을 만나면 — 문장을 셋으로 가른다

```text
   ①  step.state == "SKIPPED" 이고 chosen 이 거짓   「경로가 갈려 안 갔다」
   ②  step.state == "SKIPPED" 이고 chosen 이 참     「골랐는데 못 닿았다」
   ③  그 밖                                        「돌았고 아무 말도 안 했다」
```

**상태로 미리 거르고 요청을 아끼지 않는다.** ③ 은 총 길이를 실제로 봐야 알고,
①②도 `GET log` 가 200 에 0 을 내므로 부르는 값이 싸다. **요청을 아끼려다
셋째를 못 가르면 화면이 「안 갔다」와 「갔는데 조용했다」를 합친다.**

## 4. 그리기 — 부르기만 한다

답 1 = A. **이 유닛이 그리는 코드를 0 줄 짓는다.**

```text
   사건 열    window.enodeCard.renderEvents(container, events, {open, onToggle})
   원문 토글   pre.textContent = step.data      렌더러 밖이다 (U8 의 R36)
   걷힌 줄    「본문 N 개가 걷혔다 (M 바이트)」  사건 열 위에
   출처 줄    source 를 그대로.  「봉인 전」이면 그 말을 함께
```

**펼침 상태는 단계마다 따로 든다.** 열쇠가 `tool_use_id` 인데 (U8 의 R39) 같은
Run 의 다른 단계가 같은 id 를 낼 일이 없으므로 단계마다 집합 하나면 족하다.

**상태 줄을 안 부른다** — `statusLine` 의 문이 「도는 단계인가」이고 지난 것은
전부 끝난 것이다. 봉인 전 Run 을 누른 경우도 마찬가지다: 그 Run 이 도는 것은
**위의 카드**가 말한다.

## 5. 안 올 때

**세 상태를 안 합친다** — U5 가 R15 ~ R17 에서 정한 것을 이 화면에서도 세운다.

```text
   Status 가 실패했다        단계 목록이 없다.  「기록을 못 불러왔다」.  markMediator(false)
   단계 하나가 실패했다       **그 단계만** 오류로 적고 나머지는 그린다
   Run 이 없다 (404)        「그런 Run 이 없다」.  빈 화면과 다르다
```

**단계 하나의 실패가 화면 전체를 비우면 안 된다.** tar 는 통째로 오거나 안
왔으므로 그 구별이 없었고, N+1 이 되면서 생긴 자리다.

```text
   오늘의 모양   .catch(...) 가 "기록을 못 불러왔다" 하나로 접는다
   뒤의 모양     단계마다의 오류가 그 단계 자리에 남는다
```

## 6. CB2 가 이 흐름의 어디를 재나

```text
   같은 파서의 같은 모양     4절 — 도는 것과 같은 함수가 그린다
   출처가 GET 이고          1절 — 네트워크 탭에 record 가 0 이고 log 가 N 개
   tar 를 안 푼다           internal/panel 에 archive/tar 가 0 이다
   verdict.checks 가 보인다  이 유닛이 안 만진다 (Run 목록에서 온다)
   봉인 전이 적혀 있다        2절
```

**그리고 CB6 의 ⑥ 이 이것으로 닫힌다** — 「Run 이 끝난다. 제어판의 지난 작업에서
그 Run 을 누르면 같은 모양으로 읽힌다」. 그 줄의 나머지 절반(`runctl record` 의
tar 와 `GET` 의 마지막 답이 같은 바이트)은 **U8 의 측정에서 이미 초록이다** —
세 단계 전부 `cmp` 로 확인했다 (11,553 · 102 · 4,790).

---

## 7. 이 유닛이 치르는 값 하나

**봉인 전 Run 을 누르면 진행 파일 전체가 한 응답에 실린다.**

```text
   봉인 뒤   선별본이라 작다.  cb4-card-4 세 단계 합이 16,445 바이트
   봉인 전   진행 파일이라 크다.  survey 한 단계가 127,117 바이트였다
   브라우저   **루프백이다.**  제어판은 그 기계 안이라 이 크기가 안 아프다
   Mediator  N+1 요청이 그만큼 나른다.  누를 때 한 번이고 폴링이 아니다
```

**아픈 쪽이 Mediator 이고 값은 한 번의 N+1 이다.** NFR 단계가 없으므로
(유닛 정본이 스킵으로 걸었다) 이 봉투를 여기서 적어 두고 **CB2 가 밟는다.**
아프면 `data` 를 두 번째 쿼리로 미루는 것이 다음 자리다 — U8 이 현황판에서
그렇게 했다 (그쪽 답 7 = A).
