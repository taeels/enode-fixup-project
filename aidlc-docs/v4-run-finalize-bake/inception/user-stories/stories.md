# 사용자 스토리 — 최소

**왜 최소인가.** `scene-gates.md` 의 조각 0 ~ 12 와 `requirements.md` 6절이 수용 기준을
실행 명령으로 이미 적었다. 스토리가 행복 경로를 다시 쓰면 약한 사본이 되고, 갈리는 날
어느 쪽이 이기는지 정할 자리가 없다.

**조각이 안 재는 자리가 둘이다** (`user-stories-assessment.md`).

```text
   기다림의 이유    이 팩의 새 상태는 대부분 「아직 안 된다」다 — finalizing · waiting · drain ·
                   not ready · bake_in_progress.  조각은 그 상태에 옳게 들어가고 나오는지를
                   재고, 기다리게 된 사람이 어느 기다림이고 누구 때문인지 아는지는 거의 안 잰다
   바뀐 기본값      계약도 설정도 안 고친 사람의 동작이 바뀐다.  조각은 새 동작이 도는지를
                   재고, 그 사람이 바뀐 줄 아는지는 안 잰다
```

```text
   묶는 법     Persona-Based (Q3 = A).  기다리게 하는 쪽(P4)과 기다리는 쪽(P2)이 다른 묶음이다
   갈래 열     기다림 · 부재는 Q2 = B 의 첫 갈래(기다림의 이유)다 — 아직 안 된 것과 없는 것.
              기본값은 둘째 갈래다.  집행은 둘 밖의 하나로, 앞 회차의 US-11 을 잇는다
              (사람 조각을 사람이 잰다)
   FR 열      묶는 법이 아니라 추적이다.  Units Generation 이 이것으로 유닛에 앉힌다
   확인 열     초록임을 무엇으로 보는가.  조각이 이미 재면 그 조각을, 아니면 2절의 완료 조건을 가리킨다
```

모르는 보존은 안 적은 잔여와 같다.

**US-6 은 Q5 = A 의 폭이다.** 「누가 바꿨는지」는 조각 6 이 metadata 필드로 이미 잰다.
새 요구가 없다.

# 2. 새 완료 조건 열

**두 글자 약칭을 안 붙인다.** 앞 회차(`v3-run-transcript`)는 같은 것에 두 글자 약칭을
붙였는데 그 푼 말이 저장소에 없다(`CLAUDE.md` 의 glossary 규약은 그보다 이틀 앞선
2026-09-13 에 섰다). 그리고 그 약칭의 1 ~ 6 번이 Construction 루트 `aidlc-docs/taeels/`
에서 이미 쓰인다 — 이 회차의 유닛도 그 루트에 쓰므로 같은 번호가 다른 조건을 가리키게
된다. 그래서 이 회차는 「완료 조건 N」으로 풀어 쓴다.

**`requirements.md` 는 안 고친다** (Q4 = A). Units Generation 이 이것을 유닛의 완료
조건으로 내리고, 배정 안 된 조건이 0 임을 센다.

**완료 조건은 누가 무엇을 알아야 하는가까지만 적는다.** 필드 이름 · 화면 · API 모양은
Application Design 이 닫는다. `requirements.md` 8절에 이미 넘긴 항목이면 그 번호를 가리키고
사람 쪽 기준만 더한다.

| 조건 | 누가 무엇을 안다 | 스토리 | 8절 | 딛는 제약 |
|---|---|---|---|---|
| 1 | 노드 소유자가 **자기 노드 쪽에서** drain 의 출처 셋(소유자 정책 · 여유 부족 · 굽기)을 가른다 | US-1 | ④ | FR-4 는 새 광고 어휘를 안 만든다. 그래서 Mediator 응답에 출처를 싣지 않아도 이 조건은 선다 — 싣는지는 ④ 가 닫는다 |
| 2 | 노드 소유자가 노드 쪽에서 trash 와 spool 이 차지한 양과, 배경 삭제자가 도는 중인지를 본다 | US-2 | ⑨ | 크기 측정은 보고 뒤다 (5.4).  보고 전 창에 순회를 들이지 않는다 |
| 3 | 바뀐 기본값 다섯이 **그것을 겪는 사람이 읽는 자리 하나에** 적히고, 거짓이 된 문장이 남지 않는다 (아래 표) | US-3 · 4 · 5 · 9 · 10 | — | 정본 문서는 `requirements.md` 11절의 되돌림 목록이 진다.  이 조건은 정본 밖의 자리다 |
| 4 | 계약 작성자가 QUEUED 인 자기 Run 의 후보가 **점유돼서인지 drain 중이라서인지** 본다 | US-7 | — | drain 의 출처까지는 요구하지 않는다 — 그것은 광고 어휘를 늘린다 (FR-4).  Mediator 가 이미 가진 두 집합(`busyIn` · `drainingIn`)으로 선다 |
| 5 | 굽기 담당과 진행자가 waiting 인 merge 단계에서 **기다리는 형제 노드와 그 노드가 쥔 Run**, 그리고 대기 상한까지 남은 시간을 본다 | US-12 · US-15 | ③ | Mediator 는 lower 관계를 모른다 (ADR-077 「Mediator 가 lower 점유 행을 갖는다」 기각).  누구를 기다리는지는 노드 쪽에서 나온다 |
| 6 | 굽기 담당이 FAILED 로 봉인된 굽기 Run 의 id 로 **그 굽기가 재개로 lower 에 합쳐졌는지**를 노드 기계에 들어가지 않고 안다 | US-18 | — | 봉인된 Record 를 고치지 않는다 (I4).  Mediator 에 lower 를 들이지 않는다 |
| 7 | 계약 작성자가 `captured` 의 뜻을 안다 — 그 노드에만 있고, inspect-only 이고, 누가 열 수 있고, TTL 에 사라진다 | US-11 | ⑧ | 외부 descriptor 에 host 경로와 비밀을 싣지 않는다 (5.3) |
| 8 | 진행자가 합치기 조각(6 · 7 · 8)의 명령을 돌리면 **굽기를 내기 전에 대상 노드의 lower 가 출력되고, 운영 lower 면 멈춘다** | US-13 | — | 자리는 조각의 스크립트다.  `scene-gates.md` 3절 「값은 시작값이다 — Code Generation 계획이 굳힌다」 |
| 9 | 굽기 담당이 `merge_wait_timeout` 으로 끝난 굽기의 Record 에서 **build 단계의 성공과 merge 단계의 사유를 따로** 본다.  조각 8 의 확인에 이 한 줄을 더한다 | US-17 | — | Record 는 append-only 다.  새 기록 모양이 아니라 두 단계가 각자 제 결과를 갖는지를 잰다 |
| 10 | 굽기 담당이 merge 결과에서 **`ir` 을 유도하지 못한 이유**를 본다 — HEAD 에 붙은 태그가 0 인지, 형식에 맞는 태그가 여럿인지 | US-19 | ⑩ | IR 은 계약 칸이 아니다 (FR-9).  이유를 적을 뿐 유도 규칙을 안 바꾼다 |

## 완료 조건 3 의 다섯 줄

```text
   #   바뀐 것                     겪는 사람     지금 그 사람이 읽는 자리의 문장
   ①   min_free_gb 가 노드 전체를   노드 소유자   packaging/macos/examples/*.yaml 넷이 「디스크가 이 아래로
       drain 시킨다                              떨어지면 빌드 능력을 광고에서 뺀다」고 적는다.  거짓이 된다
   ②   scratch 가 다른 filesystem   노드 소유자   없다.  어제까지 ready 였다
       이면 not ready
   ③   checkpoint 기본 on-failure   노드 소유자   없다.  켜는 자리가 곧 끄는 자리여야 한다
       · 48시간 · 보존 용량 20%
   ④   명령 단계의 effect 기본값     계약 작성자   없다.  workspace.diff 는 조용히 안 나온다
       build/test — diff 와 변경
       목록을 안 낸다
   ⑤   agent 단계의 걷기가 Git      계약 작성자   없다.  그 훅은 workspace.changed 를 읽는다
```

**① 이 이 표에서 유일하게 「있는 문장이 거짓이 되는」 줄이다.** 나머지 넷은 없던 문장을
적어야 하고 ① 은 있는 문장을 고쳐야 한다. 고치지 않으면 예시를 베낀 새 노드 소유자가
옛 뜻을 배운다.

## 완료 조건이 FR 과 닿는 자리

```text

                 조건 1 은 노드 쪽에서 서고, 조건 4 는 광고 어휘를 안 늘리고 Mediator 의 진행 조회만
                 넓힌다.  둘 다 그 문장을 안 깬다.  조건 4 는 Mediator 변경이 는다 — Units Generation 이
                 그 유닛을 센다
   조건 5 · 6     Mediator 가 lower 를 모른다는 정본의 선을 지키려면 답이 노드 쪽에서 나와야 한다.
                 노드 기계 밖으로 그것을 어떻게 내는지가 Application Design 의 몫이다
```

# 3. 순연 — `decisions.md` 에 더할 행 (Q5 = A)

**스토리로 안 쓴 것 하나를 이름으로 남긴다.** 노드 소유자가 자기 lower 를 바꾸는 굽기를

「대여 대상: 누구에게 빌려주나 는 인증을 요구한다」.

# 4. INVEST 와 사상

## 4.1 INVEST

```text
   Independent   열아홉이 서로를 안 기다린다.  완료 조건을 나누는 스토리(US-12 · US-15)도 각자 다른
                 사람이 다른 이유로 읽는다
   Negotiable    「누가 무엇을 아는가」만 적고 어디에 어떤 이름으로 싣는지는 안 적는다
   Valuable      열아홉 전부 사람이 잘못 읽거나 모르고 지나가는 것을 막는다
   Estimable     FR 열이 붙어 있어 어느 코드가 움직이는지 보인다
   Small         하나가 응답 필드 하나, 문장 하나, 게이트 확인 한 줄이다
   Testable      확인 열이 조각 번호나 완료 조건 번호를 가리킨다.  확인 열이 빈 스토리 0
```

9)을 함께 진다.
