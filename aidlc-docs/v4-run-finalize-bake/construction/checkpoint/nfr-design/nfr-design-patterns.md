## 1. D1 — 예약을 세션을 열 때로 (답 1 = A)

| 때 | 하는 일 | 판정의 창 | 측정 (계획 2.2 · NFR 계획 2절) |
|---|---|---|---|
| 세션을 연 뒤 (`claim.go:712` · `bake_build.go:196`) | 정책이 off 가 아니고 runtime 이 지원하고 spool 을 받아들인 노드면 예약 — ID · 항목 폴더 · 항목 잠금 · `reserved` 기록. 실패하면 errno 를 들고 단계는 그대로 돈다 | 밖 (명령 앞) | p50 67 µs · p99 168 µs · 부하에서 초 단위로 멈출 수 있다 — 그만큼 명령의 시작이 늦다 |
| 명령 · Finalize | 오늘 그대로 | — | — |
| Finalize 뒤 · Close 앞 | 규칙 1절 (요구하나) · 2절 ② ~ ④ — stat 둘 · statfs · `usage.json` 읽기 | 안 | stat 과 statfs 6 µs · 읽기 15 µs |
| Close 안 | helper 가 끝난 뒤 `By` 를 보고 rename 한 번 (규칙 2절 ⑤) | 안 | 10 µs · 부하에서 최대 60 ms — 작업 폴더를 trash 로 옮기는 오늘의 rename 과 같은 종류 |
| `closedAt` 뒤 | 확정 (`kept` 기록 · 잠금 놓기) 이나 버림 (규칙 2절 ⑥ ⑦) | 밖 — `closedLate` 는 `closedAt` 으로 정한다 (`claim.go:884`) | 62 µs |
| 보고 뒤 | 요구하지 않았거나 칸이 없는 끝의 예약을 버린다 — 기록 · 잠금 파일 · 폴더 | 밖 | p50 36 µs · p99 91 µs |

**대 본 것 — 답 뒤에도 그대로 성립한다**

| 규칙 | 어떻게 |
|---|---|
| on-failure 의 뜻 | 예약은 판정이 아니다. 요구하는지는 닫을 때 규칙 1절이 사실 (exit · 미완주 · 빠진 산출물 · Finalize 오류) 로 정한다 |
| ADR-076 §4 「rename 앞이면 `rejected`(`lease_budget`)」 | 규칙 2절 ③ (Close 앞) 과 `Keep.By` (Close 안 · rename 바로 앞) 그대로 |
| ADR-076 §4 「rename 뒤 확정 전에 소진이면 `failed`(`lease_budget`)」 | 규칙 2절 ⑥ 그대로 — 확정이 `closedAt` 뒤로 가도 마감은 같은 `spec.Deadline` 이다 |
| ADR-076 §4 의 3 · 결정 2-7 (보고 전에는 여유와 보존 총량만) | 받아들임은 닫을 때 그대로. 예약은 받아들임이 아니다 — 예약이 있어도 ④ 에서 거절할 수 있다 |
| ADR-076 §4 「임대 창에서는 O(1) 소유권 이전만」 | 창에 남는 것이 stat · 작은 읽기 · rename 하나다 |
| ADR-076 §5 「부분 상태와 완료 상태를 구분」 | `reserved` 가 도는 단계의 자리까지 넓어질 뿐 구분은 같다. 주인 없는 예약은 기동 조정이 거둔다 (규칙 9절) |
| FR-10 끝 줄 · NFR P2 | 느린 일 (폴더 · 잠금 · 기록 쓰기) 이 판정의 창 밖에 있다 |

**보이는 것** (답 1 의 선택지 그대로)

- 성공한 단계마다 spool 에 폴더 하나를 만들었다가 보고 뒤에 지운다
- 도는 단계의 예약은 `list` 에 안 보인다 — 항목 잠금이 쥐어진 `reserved` 를 뺀다. 주인이 없는 것만 `incomplete` (규칙 13절)
- 예약이 세션을 열 때 실패하면 단계는 돌고, 닫을 때 요구하면 `failed`(`io`) 와 그때의 errno 문장 (규칙 2절 ⑤)

**예약을 안 하는 노드** — 정책 off · native · spool 을 거절한 노드 (NFR C8). 닫을 때의 판정은 규칙 2절대로 `not_requested` ·
`unsupported` · `failed`(`io`) 를 낸다.

## 2. D2 — spool 잠금은 읽기와 적기에만

| 판정의 차례 (규칙 6절) | 잠금 |
|---|---|
| 1 기록 읽기 · 만료 · 측정할 목록 | 쥔다 → 놓는다 |
| 2 측정 (helper) | 쥐지 않는다 |
| 3 ~ 7 측정값 적기 · 퇴출 · `usage.json` · 상태 파일 | 다시 쥔다. 기록을 다시 읽고, 그새 형제가 퇴출하거나 만료한 항목의 측정값은 버린다 |

- 측정은 읽기만이라 잠금 없이도 트리를 바꾸지 않는다. 형제가 같은 항목을 함께 측정하면 일이 두 번일 뿐 값은 같다
- 기다리는 쪽은 형제의 판정과 조정의 짧은 읽기 · 적기뿐이다 (NFR P5). 찬 캐시의 측정 시간 (NFR 5절) 은 판정 한 번을 늘릴 뿐 남을 막지
  않는다

## 3. D3 — 요약 `usage.json`

- **쓰는 쪽** — 판정의 끝 (차례 7) 에 spool 잠금 안에서. `kept` 의 측정한 바이트 합 · inode 합 · 시각. 임시 파일과 rename · 0600 ·
  fsync 없음 (NFR P4). 경로를 담지 않는다
- **읽는 쪽** — 닫을 때의 받아들임 (규칙 2절 ④ · 5절). 잠금을 쥐지 않는다. 없거나 못 읽으면 0 으로 센다
- **닫을 때 읽는 까닭** — 계획 3.2 는 「D1 이 A 면 창 밖 (열 때) 에서 읽는다」고 적었다. 단계가 몇 시간 돌면 열 때의 값은 낡는다. ADR-076
  §4 의 3 은 「현재 보존 총량」이다. 작은 파일 읽기는 15 µs 이고 쓰기처럼 journal 을 기다리지 않는다
- 어느 노드의 판정이든 spool 전체의 기록을 읽으므로 (규칙 6절 1) 형제의 측정한 보존본이 든다. 측정 전인 가장 새 것은 여전히 0 이다 —
  넘침은 다음 판정까지다 (NFR P7)
- 조회 (`list` · `show`) 는 이 파일을 안 읽는다. 조정은 이 파일을 항목으로 보지 않는다 (ID 모양이 아니고 폴더가 아니다)

## 4. D4 — 깸과 측정 helper

- 판정 고루틴 하나. 깸은 자리 하나짜리 채널이다 (`scratch/deleter.go:68` · `:81` 과 같다). 돌 때 온 깸은 끝난 뒤 한 번으로 합친다 —
  보고 뒤 · 10분 · 조정 뒤 · 예약 버리기 뒤
- 측정 helper 는 항목 하나에 하나 · 차례로 · IO 우선순위 idle 과 CPU 19 (`trash_linux.go:53` 과 같다). 입구는 trash-helper 의 측정 동작
  (흐름 5절). 삭제자의 helper 와 겹쳐 돌 수 있다 — 둘 다 idle 이다
- helper 를 못 띄우면 그 판정을 멈추고 다음 깸을 기다린다 (규칙 6절 · 삭제자와 같다)
- 예약 버리기는 판정 고루틴이 한다 — 보고 뒤의 깸 하나가 버리기와 판정을 함께 한다
