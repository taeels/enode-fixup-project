# 사상 — 기능과 게이트가 어느 유닛에 앉나

**User Stories 를 건너뛰었다** (실행 계획 3절). `scene-gates.md` 의 조각 일곱이
실행 명령으로 적힌 수용 기준이라 스토리는 그것을 약한 형태로 다시 쓰는 일이 된다.

그래서 사상하는 것은 스토리가 아니라 **기능 3.1 ~ 3.7 과 조각 게이트 CA0 ~ CA6** 이다.

---

## 0. 스토리 -> 유닛

User Stories 를 최소 형태로 돌렸다 (2026-09-12). 정본은
`inception/user-stories/user-stories.md` 이고 페르소나는 `personas.md` 셋이다.

| 스토리 | 페르소나 | 유닛 | 확인 |
|---|---|---|---|
| US-1 선언이 함대에 보인다 | 노드 소유자 | U3 | CA2 |
| US-2 잘못 적으면 노드가 안 뜨고 사유를 본다 | 노드 소유자 | U3 | U3 완료 조건 |
| US-3 안 뜨는 서버의 사유를 노드 로그에서 본다 | 노드 소유자 | U3 | CA2 |
| US-4 함대의 `mcp.<이름>` 을 열거해 본다 | 계약 작성자 | U3 | U3 완료 조건 · CA3 |
| US-5 지금 실제로 잡히는지 제출 전에 본다 | 계약 작성자 | (기존) | `runctl dry-run` |
| US-6 없는 이름을 요청하면 사유와 함께 실패한다 | 계약 작성자 | U4 | CA4 |
| US-7 타입을 틀리게 적으면 제출에서 걸린다 | 계약 작성자 | U2 | U2 완료 조건 |
| US-8 팩의 스킬이 실제로 떴는지 본다 | 계약 작성자 | U5 | CA5 |
| US-9 팩이 규약을 어기면 실패하고 사유를 본다 | 계약 작성자 | U5 | U5 완료 조건 |
| US-10 봉인만 열어 무엇으로 돌았는지 안다 | 진행자 | U5 | CA6 |

**배정 안 된 스토리 0.** U1 에 스토리가 없는 것은 맞다 — 가짜 홈은 사람이 적는
값이 하나도 없다 (`features.md` 3.1 「여는 값을 두지 않는다」).

## 1. 기능 -> 유닛

| 기능 | 무엇인가 | 유닛 | 쪼개졌나 |
|---|---|---|---|
| 3.1 | 가짜 홈 | U1 `isolation` | 아니오 |
| 3.2 | MCP 허용목록 | U1 (쓰는 자리) · U4 (정하는 자리) | **예** |
| 3.3 | 노드 선언과 광고 | U3 `advert` | 아니오 |
| 3.4 | 워크스페이스 감지 | U4 `sources` · U5 (마지막 줄) | **예** |
| 3.5 | 계약 문법 | U2 `contract-vocab` | 아니오 |
| 3.6 | 팩 | U5 `pack` | 아니오 |
| 3.7 | 기록 | U5 `pack` | 아니오 |

**사상되지 않은 기능 0.**

### 1.1 쪼개진 둘

3.2 와 3.4 가 유닛 둘에 걸린다. **3.4 는 마지막 줄 하나만 갈린다** — 워크스페이스
`.claude/skills/` 를 하네스가 스스로 읽는지 재고 안 읽으면 팩으로 나르는 줄이다.
그것은 CA5 가 재므로 U5 의 완료 조건에 있다 (`requirements.md` FR-4 의 수용 기준도
「CA4 의 둘째 줄 · CA5」로 적었다).

### 1.2 3.2 가 쪼개진 이유

`application-design.md` 1절이 이 설계의 뼈대를 「결정과 쓰기를 가른다」로 적었다
(Q4 = A). 3.2 허용목록은 그 갈래를 정면으로 타는 유일한 기능이다.

```text
   쓰는 자리   U1   Instrument 가 <dir>/mcp.json 을 쓰고 플래그를 낸다.
                    정책을 다시 판단하지 않는다.  CA1 이 빈 목록으로 이것을 잰다
   정하는 자리  U4   resolveComponents 가 출처를 합치고 거절한다.
                    파일을 안 만진다.  CA4 가 이것을 잰다
```

**쪼갠 것이 게이트를 싸게 만든다** — CA1 은 계약 어휘 없이 서고, CA4 는 파일을
안 쓰는 시험으로 대부분 덮인다.

## 2. 조각 게이트 -> 유닛

| 게이트 | 무엇을 재나 | 집행자 | 대상 | 닫는 유닛 |
|---|---|---|---|---|
| CA0 | 기동이 안 깨졌다 | 기계 | 스크래치 | **유닛 다섯 전부** |
| CA1 | 끊긴다 | 사람 | 스크래치 | U1 |
| CA2 | 광고한다 | 사람 | 스크래치 | U3 |
| CA3 | 고른다 | 사람 | 함대 | U2 (절반) · U3 (완결) |
| CA4 | 연다 | 사람 | 스크래치 | U4 |
| CA5 | 싣는다 | 사람 | 스크래치 | U5 |
| CA6 | 한 장면 | 사람 | **사내 함대** | U5 |

**담당 없는 게이트 0.**

### 2.1 CA3 만 유닛 둘에 걸린다

CA3 은 네 줄을 재는데 그 넷이 두 유닛에서 온다.

```text
   U2 가 닫는 것   agent 에 모르는 키 -> 400
                   runctl example mcp && runctl lint -> ok
   U3 이 닫는 것   requires 에 mcp.<이름> 을 적은 계약이 그 노드에만 간다
                   없는 키 -> 422 (후보 0)
```

**U2 뒤에 CA3 을 절반만 재고 넘어간다.** 그것이 게이트를 빨간 채로 넘기는 것은
아니다 — 유닛의 완료 조건은 「그 유닛이 지는 줄」이고, CA3 조각 전체는 U3 에서
초록이 된다. `unit-of-work.md` 2절 · 3절이 각각 자기 줄을 적었다.

### 2.2 CA0 가 다섯 번 도는 이유

계획 Q5 = A. `internal/enode` 의 커버리지 80% 하한을 **유닛 단위로 집행**한다.
근거는 `unit-of-work.md` 6절.

### 2.3 사람이 실제로 띄워야 초록인 것 넷

`init` 줄은 **`logs/` 에서 기계가 읽는다** — U1 이 `Argv` 에 플래그 한 줄을
더하기 때문이다 (`decisions.md` 6절 ⑮). 사람이 하는 것은 그 줄을 **보고 판정하는
일**이고, 손으로 하네스를 다시 띄우는 복제본 경로는 쓰지 않는다.

```text
   CA1   U1   init 의 mcp_servers 가 비어 있다.  노드 둘에서 각각
   CA2   U3   눈 검증 S1 — 현황판 · 제어판의 칩
   CA4   U4   init 의 mcp_servers 이름이 요청한 하나뿐이다
   CA5   U5   init 의 slash_commands 에 팩의 스킬 · mcp_servers 에 팩의 서버
```

**보류로 안 넘긴다** (`scene-gates.md` 4절).

## 3. 요구 문서의 확정이 어느 유닛에 앉나

`requirements.md` 가 확정으로 건 줄과 `decisions.md` 6절의 행 열여덟이다.

| 확정 | 유닛 |
|---|---|
| FR-1 계장 실패와 독립이다. 홈은 갈아끼워져 있고 비어 있다 | U1 |
| FR-1 자격증명 원본이 없으면 아무것도 안 한다 | U1 |

## 4. 팩이 「안 하는 것」이 유닛에 안 새는가

`constraints.md` 의 제외 여덟 범주와 대조했다. **새는 유닛이 없다.**

```text
   1 계정 커넥터를 여는 경로     U1 이 값으로 닫는다.  이름 차단은 안 한다
   2 자격증명 주입              U1 은 복사만 한다.  값을 계약·허용목록·광고에 안 싣는다
   3 부칠 수 있는 것의 광고      U3 은 노드 선언만 광고한다.  U4 의 워크스페이스는 안 싣는다
   4 MCP 의 내용을 아는 것       U3 의 mcpUp 은 tools/list 를 안 부른다
   5 팩의 운반 경로 추가         U5 는 이미 있는 blob 경로만 쓴다.  새 라우트 0
   6 두 번째 하네스             어느 유닛도 어댑터를 안 늘린다
   7 중앙 설정                  Mediator 의 하네스·MCP 항목이 0 줄 그대로다
   8 기존 계약 변경             U5 가 새 Reason 을 안 만든다.  매처를 안 건드린다
```

## 4.1 security-baseline 준수 — 이 단계

`core-workflow.md` 의 Enforcement 가 단계마다 요구한다. Units Generation 은 코드를
안 짓고 경계와 행렬을 내므로 규칙 대부분이 N/A 이고, **걸리는 것은 셋**이다.

| 규칙 | 판정 | 근거 |
|---|---|---|
| SECURITY-05 입력 검증 | 준수 | 검증 표면 셋이 전부 유닛에 앉았다 — `readPack`(U5) · `enode.yaml` 의 `mcp:`(U3) · `agent.mcp`/`agent.pack` 의 타입(U2) |
| SECURITY-06 최소 권한 | 준수 | 팩의 서버도 `agent.mcp` 필터를 탄다 (`application-design.md` 4.4). 요청 안 한 서버가 0 이다 |
| SECURITY-08 접근 제어 | 준수 | 팩이 노드 선언 이름을 덮으면 거절한다 (4.5). 소유권 역전 경로를 U5 가 막는다 |
| SECURITY-15 예외 처리 | 준수 | 실패 등급의 기본이 치명이다 (4.1). U1 의 완료 조건이 그것을 잰다 |
| SECURITY-10 무결성 | 준수 | 팩이 새 표면이고 `readPack` 의 SEC-A 가 유닛 U5 에 앉았다 |
| 그 밖 아홉 | N/A | 이 단계는 문서만 낸다 — 네트워크 · 웹 표면 · 자격증명 저장 · 알림 경로를 이 단계가 만들지 않는다 |

## 5. 구조 불변식이 유닛마다 참인가

```text
   새 패키지 0        다섯 다 참.  mcp.go 는 internal/enode 안의 새 파일이다
   임포트 금지 넷      다섯 다 참.  새 임포트 간선이 0 이다.
                     다만 기계가 재는 것은 셋이다 — api/ui -> store 는 시험이 없다
   라우트 0           다섯 다 참.  세는 명령은 internal/api/*.go 전체의
                     mux.HandleFunc 와 mux.Handle( 을 함께 센다 (오늘 26)
   하네스 exec 은 한 자리  다섯 다 참.  runHarness 하나가 하네스를 띄운다
```

**「프로세스를 띄우는 코드는 `runner.go` 하나다」로 적으면 거짓이다.**
`internal/enode` 만 봐도 여덟 자리가 프로세스를 띄운다 — `runner.go:93`(하네스) ·
`claim.go:614`(명령 단계) · `claude.go:115`(`--version`) · `claude.go:160`
(`auth status`) · `repoid.go:109` · `identity.go:121` · `diff.go:142` ·
`workspace.go:151`. 참인 좁은 형태는 `harness.go:174` 주석이 이미 적어 둔
**「하네스 exec 은 `runHarness` 하나」**다. `constraints.md` 의 「어댑터에 exec 을
두지 않는다」도 `claude.go` 에서 이미 깨져 있다 — 이 팩이 깨는 것이 아니다.
**유닛마다 도는 검사로 굳힐 때 이 좁은 형태를 쓴다.**
