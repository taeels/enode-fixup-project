# demo-back 검증 규칙

**상태**: 승인된 규칙을 구현·로컬 검증했다. 보안 범위는 decisions §3·§8의 수락·예외를 상속한다.

| 규칙 | 처리 | 구현 후 증거 |
|---|---|---|
| DEMO-BR-01 공개 표면 | Config.Demo에서만 등록, 일반 submit·asks 인증 유지 | 두 모드에서 라우트·인증 회귀 |
| DEMO-BR-02 allow-list | 공개 별칭 둘, 고정 example·주입 함수만 허용 | 임의 계약·경로 조작·unknown/duplicate key 거절 |
| DEMO-BR-03 이름 | 기존 Guest 형태만 받으며 동일 값을 컨텍스트·음원 입력에 전달 | 표시 이름과 주입 값·DB 값 일치 |
| DEMO-BR-04 계약 불변 | 사본의 식별·승인된 이름 위치만 변경 | 원본과 비교, requires·needs·success_when 보존 |
| DEMO-BR-05 재시도 | 같은 요청은 같은 ID, 새 요청은 새 ID | 응답 유실·동시 재시도에서도 Run 하나 |
| DEMO-BR-06 선행 부족 | 픽스처·토큰 미설정은 503 | fallback 계약·브라우저 토큰 없이 실패 |
| DEMO-BR-07 접수 재사용 | 기존 submit 응답·queue·DB 트랜잭션 보존 | 201/200/202와 409/422/503, 실제 QUEUED 승격 |
| DEMO-BR-08 자원 경계 | 본문 4 KiB, 공개 제출 전용 전역 2 req/s·burst 4 | 읽기 한도와 독립, 초과 429/Retry-After: 1 |

전용 제출 한도는 obs의 token bucket 구현을 재사용하는 담당 설계 값이다.
함대 polling의 버킷과 공유하지 않으며 IP·Guest 이름별 권한/쿼터를 만들지 않는다.
한 관람객이 전역 버킷을 소진할 수 있는 한계는 남고 CP10 동시 시연으로 검증한다.
단순 더블클릭뿐 아니라 공개 호출 반복을 입력 오용 사례로 다룬다.

이름 주입은 픽스처에서 지정한 argv의 독립 원소·env 값·구조화 입력처럼 데이터
위치에만 한다. prompt 문자열이라면 고정 안내 안의 이름 데이터로만 넣고, 실제
셸 명령/파일 경로에 붙이지 않는다. 픽스처에 안전한 주입점이 없으면 진행자에게
필요 형태를 제시하고 활성화하지 않는다. 새 CLI·하드웨어 동작은 이 유닛에서 만들지 않는다.

| 보안 규칙 | 설계 적용 |
|---|---|
| SECURITY-04 | HTML은 UI 유닛의 기존 헤더. 이 라우트는 기존 JSON 응답 |
| SECURITY-05·13 | 본문 제한·엄격한 JSON·필드 검증·고정 픽스처·기존 매개변수 SQL |
| SECURITY-08·12 | 데모만 공개, 서버 토큰 주입, 이름은 권한 아님. 결정표의 수락 범위 유지 |
| SECURITY-11 | 반복 제출·대형 본문·임의 계약 오용을 위 경계로 제한 |
| SECURITY-15 | 접수 결과 미확인과 거절 구분, 픽스처 미제공 시 실패, 기존 자원 정리 |
| SECURITY-01·03·07 | 프로젝트의 기록/예외 범위 상속. 토큰·본문 로그 금지 |
| SECURITY-02·06·09·10·14 | 새 인프라/역할/의존을 만들지 않음. 기존 서비스·CI·운영 검증은 별도 |

위 표는 FD의 대응이다. 실제 보안 검사·커버리지·장면 통과를 뜻하지 않는다.
