# ui 디자인 타깃과 이번 계획의 범위

**상태**: 사용자 범위 확인 질문에 따른 대조 기록. 데모 FD 완료나 코드 생성
승인을 의미하지 않는다. 아래의 이전 8단계 비교는 범위 보완의 근거다.
2026-09-09에 [화면 설계](frontend-components.md) §6~9로 D1~D5와 웹캠 전체
조작을 보완했고, 현재 코드는 [11단계 계획](../../plans/ui-code-generation-plan.md)을 따른다.

**추가 구현 입력**: 사용자가 지정한 `3d-view` 워크트리의 `8985694`를
[재사용 검토](3d-view-reuse-review.md)했다. 최종 화면 기준은 팀원 demo pen,
3D 표시·그래프 탐색의 구현 기반은 그 코드에서 선별하는 방향으로 보완한다.

## 1. 최종 타깃과 구현 순서

runixs의 ui는 실 함대와 공개 데모 두 모드를 포함한다. 최종 대회 시연 화면은
팀원이 만든 `design/enode-demo.pen`을 따른다. `requirements/decisions.md` §8의
대회 데모 전환과 `construction-roster.md`의 W1/W3 배정이 근거다.

직전 W1 FD에서 직접 읽고 반영한 시안은 `design/enode-ux.pen`의 S0·S1·S1b·S2다.
데모 pen의 존재와 후속 의존은 기록했지만, D1~D5의 레이아웃·조작을 그 8단계
계획에 구현 대상으로 넣지는 않았다. 공통 색상이나 노드 데이터 규칙을 쓴 것만으로
데모 디자인을 반영했다고 부르지 않는다.

이번 대조에서 `enode-demo.pen`의 프레임·문구·변수를 읽고 D2/D5 export를
시각적으로 확인했다. 요구 팩의 S6(함대 3D)·S7(작업 그래프 3D)는 이 pen의
D2·D5에 대응한다. W3는 연동·완료 순서이며 디자인 검토까지 미룰 이유는 아니다.

## 3. obs 전에도 준비할 부분

데모 화면의 구성·3D 표현·선택/전환·투어·모달·웹캠 영역의 크기 변경은 로컬의
명시적인 합성 입력으로 설계하고 검증할 수 있다. 실제 작업 접수·큐 승격·노드
상태·방송 수신은 해당 서비스 연결 뒤 검증한다. 합성 동작을 실제 제출 성공이나
실시간 방송으로 표시하지 않는다.

데모 FD를 보완할 때 W1에서 만든 노드/Run/단계/질문 의미 모델과 표시 규칙을
공유할 후보로 삼는다. 2D 전용 화면 구조에 인증·조회 코드를 붙여 데모 3D에서
다시 작성하게 만들지 않는다. 실 함대 Bearer와 공개 데모의 서버측 토큰 주입은
각 모드의 경계로 유지한다. 정확한 공용 파일 분리는 후속 데모 코드 계획에 적는다.

## 4. 시안과 확정 요구의 차이

- pen의 `user_4821` 예시는 확정된 랜덤 2단어 Guest 이름으로 표시한다.
- RUN 카드의 submitter는 같은 Guest 이름이다. 모달에 이름 입력을 추가하지 않는다.
- 단계의 RUNNING 예시는 실제 단계 enum인 CLAIMED를 쓴다. Run 상태는 RUNNING이다.
- 페이지네이션의 기획 미정 자리는 구현 대상에 추가하지 않는다.
- 투어의 “꺼진 자원” 문구로 중앙이 프로세스 종료를 직접 안다고 표현하지 않는다.
  노드 광고의 관측·만료 의미를 보존한다.
- sandbox는 광고에 명시된 값만 표시한다. 값이 없으면 미제공이며 격리 보장을 만들지 않는다.

디자인 원본 수정 권한은 진행자에게 있다. 이 대조는 `.pen`을 변경하지 않는다.
데모 FD·제출 계약은 승인됐고 UI 1~8을 구현했다. sandbox 출처도 2026-09-09
최태양님의 승인을 사용자에게서 전달받았다. 실제 픽스처 c7a237d와
demo-back 연결도 완료했다. 방송·실제 장비 광고와 공동 장면은 현재 코드 계획을 따른다.
