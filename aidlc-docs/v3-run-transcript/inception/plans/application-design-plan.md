## 1. 착수 전 실측 — 코드를 먼저 읽었다

**`requirements.md` 8절이 「사람에게 물을 것이 아니다. 답이 설계에서 나온다」고
적었다.** 그래서 물을 것을 고르기 전에 그 답이 코드에 이미 있는지부터 봤다.
다섯이 나왔고 **그중 넷이 질문을 지웠고 하나가 질문을 하나 만들었다.**

### 1.1 링은 단계마다 비워진다. 진행 파일은 안 비워진다

```text
   claim.go:456        새 단계가 시작할 때 w.ring.Reset() 이 돈다
   transcript.go:148   Reset 은 total 을 0 으로 하고 gen 을 올린다
   record.go:59        AppendLog 은 O_APPEND 다.  경로에 attempt 가 없다
   claim.go:469        blob 은 %02d.%d-%s 로 시도를 가른다.  로그만 안 가른다
```

**재시도가 그 둘을 갈라 놓는다.** 같은 단계가 두 번 돌면 링은 비워져 시도 2 만
보이고 진행 파일은 시도 1 뒤에 시도 2 가 이어 붙는다. 제어판은 링을 보고 현황판은
진행 파일을 보므로 **CB4 의 「같은 문장이 같은 시각 흐른다」가 그 순간 깨진다.**
Q1 이 이 자리다.

### 1.2 봉인은 삭제까지 막는다 — 남은 파일은 영원히 남는다

```text
   record.go:156   seal(dir) 이 Walk 로 모든 파일을 0444, 모든 디렉터리를 0555 로 만든다
   record.go:196   unseal 의 주석 — 「봉인은 삭제까지 막는다 ... 보관 정책이 생기면
                   여기가 그 입구다」.  오늘 보관 정책이 없다
```

진행 파일을 `run-<id>/` 안에 두고 지우는 것을 한 번이라도 놓치면 그 원문은
**0444 로 굳어 아무도 못 지운다.** 잔여 ① 의 「봉인 때 지워진다」가 그 Run 에서만
영구가 된다. Q2 가 이 자리다.

### 1.3 껍데기를 짓는 코드가 이미 있다

```text
   runner.go:315   selectLogs — 걸러 짓는 쪽
   runner.go 안    parseEventLine · eventShell · elidedMarker 셋이 그 안에 산다
```

파서가 읽어야 하는 **껍데기의 모양을 짓는 코드가 이미 `internal/enode` 에 있다.**
`internal/transcript -> internal/enode` 는 임포트 금지이고 반대는 허용이다. Q4 가
이 자리다.

### 1.4 질문을 지운 사실 넷

```text
   D3 헤더 이름          Sealed(runID) 하나로 봉인 전후가 갈린다 (record.go:76).
                        핸들러가 그 값을 헤더로 옮기면 된다.  설계가 답한다
   D4 AppendLog 호출자   api.go:887 하나다.  시그니처를 바꿔도 부딪히는 자리가 하나다
   청크의 tee 자리       claim.go:794 가 w.transcript() 를 Job.Transcript 로 넘긴다.
                        FR-5 가 「같은 tee 한 겹에서」로 이미 정했다 — io.MultiWriter 다
   오프셋의 진실         FR-5 가 「응답이 총 길이를 돌려주고 노드가 그 값으로 맞춘다」로
                        이미 정했다.  서버가 진실이다
```

### 1.5 화면이 재는 것 중 바이트에 없는 것이 있다

NC-1 (경과) 과 NC-6 (마지막 갱신) 은 **사건 바이트에서 안 나온다.** 시계가 있어야
나온다. 파서에 시계를 넣으면 그 패키지가 결정적이지 않게 되고, 화면 둘이 각자
계산하면 「파서는 하나다」가 그 자리에서 깨진다. Q3 이 이 자리다.

## 2. 이 단계가 정하는 것 · 안 정하는 것

**정한다.**

```text
   진행 파일의 자리와 수명       어디 살고 누가 지우고 언제 지우나 (D1 · Q2)
   재시도의 경계                진행 파일이 시도를 어떻게 가르나 (D7 · Q1)
   PUT 의 갈림                  기존 라우트에서 청크를 어떻게 가르나 (D2)
   GET 의 출처 표시              봉인 전후를 응답이 어떻게 말하나 (D3)
   AppendLog 의 겉면            총 길이를 내고 총 길이로 상한을 건다 (D4)
   파서 패키지의 경계            무엇이 들어오고 무엇이 화면에 남나 (D5 · Q3 · Q4)
   의존과 통신                  여섯 경로의 호출 방향.  임포트 금지 여섯을 안 깬다
```

**안 정한다** — 건드리면 옮겨 적기가 된다.

```text
   팩과 요구가 값으로 닫은 것    폴링 간격 셋 · 청크 주기와 64 KiB · 링의 형식과
                               크기와 0600 · 사건 종류 여섯 · 제외 일곱 범주
   Functional Design 몫         사건 모형의 필드 · 진행 파일의 형식 ·
                               enode.elided 의 그리는 규칙 · NC-1 ~ NC-6 의 표시 모양
   NFR Requirements 몫          N1 함대 규모 · N2 진행 파일의 디스크 수명
   Units Generation 몫          유닛 분해와 파일 행렬.  여기서 안 가른다
```

## 3. 산출물 계획 (체크박스)

규칙이 요구하는 필수 산출물 다섯이다. **4절 질문의 답이 들어온 뒤 생성한다.**
