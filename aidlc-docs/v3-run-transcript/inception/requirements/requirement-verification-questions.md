# Requirements 확인 질문 — 트랜스크립트 (v3-run-transcript)

팩의 `features.md` 5절은 **미정이 없다**고 적는다. 값으로 보면 맞다 — 주기 ·
간격 · 형식 · 라우트 모양을 `decisions.md` 1 ~ 2절이 전부 닫았다.

그런데 **팩이 딛고 선 코드가 팩을 쓴 뒤에 움직였다.** 짝 팩
(`v3-run-harness-components`)이 유닛 다섯을 `main` 에 넣으면서 이 팩의 전제
다섯을 뒤집었고, 그중 **둘은 값이 아니라 결정**이다 — 짝 팩의 사용자 결정
⑰ · ⑱ · ⑲ 가 이 팩의 가치 고정점과 정면으로 부딪친다. 에이전트가 혼자
고를 자리가 아니다.

그래서 여기서 묻는 것은 셋이다. **질문 1 과 2 가 이 회차의 범위를 정하고,
질문 3 이 운영을 정한다.** 나머지 교정은 묻지 않고 이 문서 끝의 「확인된
사실」에 적는다 — 팩의 게이트 규칙(권장을 벗어나면 근거를 적는다)이 그 자리다.

각 질문의 `[Answer]:` 뒤에 글자를 적는다. 맞는 것이 없으면 `Other` 를 고르고
설명을 적는다.

# 부딪치는 자리 — 먼저 읽는다

```text
   이 팩이 원하는 것      사람이 도는 동안 읽을 수 있는 문장.  제어판과 현황판 둘 다
                         (features.md 1.5 · scene-gates.md 1절 ② ③ · CB1 · CB4)

   짝 팩이 정한 것        ⑰  봉인 기록으로 가는 자격증명 누출을 준수로 만든다
                         ⑱  logs/ 는 허용목록이다.  본문은 어느 사건에서도 안 남는다
                         ⑲  하네스 단계의 링 tee 를 끈다.  짝 팩이 선별과 함께 되살린다
```

⑱ 의 선별은 **이미 `main` 에서 돌고 있다** (`internal/enode/runner.go:315`
`selectLogs`). 남는 것은 이것뿐이다.

```text
   전문으로 남는다   system/init 사건 한 줄 · 마지막 result 사건 한 줄 · stderr
   껍데기로 남는다   그 밖의 모든 사건 — type · subtype · 도구 이름 · 성공 여부 · 토큰 수
   안 남는다        본문.  assistant 의 text 도 thinking 도 도구 결과도 같다
```

그래서 **팩의 세 문장이 오늘 코드에서 거짓이다.**

```text
   3.4 보안 요구   「오늘도 logs/ 에 원문이 봉인된다.  이 팩은 시점만 앞당긴다」
                   -> 원문이 아니다.  ⑱ 이 본문을 걷은 뒤다
   constraints 4   「원문이 봉인이다 (ADR-005)」
                   -> 하네스 단계는 아니다.  명령 단계만 원문이다 (claim.go:647)
   3.2 수용 기준   「같은 로그를 링에서 읽든 record 에서 읽든 같은 사건 열이 나온다」
                   -> 둘의 내용이 다르므로 같은 사건 열이 안 나온다
```

**이것은 팩의 잘못이 아니다.** 팩을 쓴 2026-09-11 에는 참이었고 ⑱ 은 09-12 의
결정이다. 다만 그 뒤 세계에서 「도는 동안 읽을 수 있는 문장」을 어디까지 흘릴
것인지는 다시 골라야 한다.

## Question 1 — 도는 동안 **중앙**이 받는 것은 본문인가 껍데기인가

팩의 3.4 는 「노드는 링에 쓰는 것과 같은 tee 한 겹에서 새 바이트를 모아
올린다」이다. 그대로 하면 **원문이 `logs/NN-*.log` 에 쌓이고 그대로 봉인된다** —
⑱ 이 닫은 문을 청크 경로로 되연다. 짝 팩이 exec 뒤 한 번에 거르던 자리
(`runner.go:260`)를 청크가 앞질러 지나가기 때문이다.

CB4 가 재는 것이 「제어판에 흐르는 문장이 **같은 시각 현황판에도** 흐른다」라
이 질문이 곧 CB4 의 뜻이다.

A) **중앙에도 껍데기만** — 청크를 올리기 전에 ⑱ 과 같은 선별을 줄 단위로
건다. 현황판과 `GET log` 는 사건 종류 · 도구 이름 · 토큰 수가 흐르고 본문은
없다. 봉인 기록은 오늘과 한 글자도 안 바뀐다. **CB4 의 「같은 문장」이 「같은
사건 열」로 약해진다** — 중앙에서는 에이전트가 무엇을 말하는지 못 읽고 무엇을
하는지만 읽는다.

B) **도는 동안만 본문, 봉인 때 걷는다** — 진행 로그를 `logs/` 와 **다른
파일**에 원문으로 쌓는다. `GET log` 가 봉인 전에는 그 파일을 낸다. 봉인할 때
그 파일은 지우고 `logs/` 에는 ⑱ 의 선별본만 들어간다. 도는 동안 중앙에서
문장을 읽을 수 있고, **봉인되어 삭제도 막히는 자리에는 본문이 안 남는다** —
⑰ 이 막으려던 것이 그것이다. 대가 셋: 파일이 단계마다 둘이 되고, 봉인
전후로 `GET log` 의 답이 바뀌며(CB3 의 「같은 바이트」가 봉인 전에만 참이다),
도는 동안은 Mediator 디스크에 원문이 앉는다. (권장)

C) **⑱ 을 무른다** — 원문을 그대로 `logs/` 에 올려 봉인한다. 팩이 쓴 그대로고
CB2 · CB3 · CB4 가 전부 글자 그대로 선다. 대가는 `security-baseline` 의
SECURITY-03 **비준수**이고, 그것은 이 워크플로에서 차단성이다 — 2026-09-12 의
사용자 결정(「준수 설계로 만든다」)을 되돌리는 일이다.

D) **중앙을 이월한다** — 3.4 · 3.5 · 3.6 · 3.7 을 빼고 제어판(3.1 · 3.2 ·
3.3)만 한다. 회차가 절반이 되고 「사용하다 보니 꼭 필요한 기능」이라던 중앙
실시간이 다음으로 간다.

## Question 2 — **링**(제어판)이 받는 것은 본문인가 껍데기인가

⑲ 가 끈 tee 를 되살리는 것은 이 팩의 일이다. ⑲ 가 **넷째 길을 이름으로 남겨
두었다** — `Job.Transcript` 가 이미 `io.Writer` 이므로 거기에 줄 단위 허용목록
래퍼를 끼우면 된다, 그리고 「짝 팩이 링을 되살릴 때 이 길을 먼저 본다」.

먼저 봤다. **그 길로 가면 CB1 이 안 선다.** 허용목록은 본문을 안 남기므로
제어판 카드에 도구 이름과 토큰 수만 흐르고, CB1 이 재는 것은 「**읽을 수
있는 문장**이 흐른다」이다. 래퍼 자체는 질문 1 의 A · B 가 어차피 쓴다 —
질문은 **그 래퍼를 링에도 거는가**이다.

링이 다른 자리인 이유 — **읽는 사람이 다르다.**

```text
   링            노드 디스크의 512 KiB 파일.  루프백 제어판만 읽는다.
                 그 기계의 소유자가 그 에이전트를 자기 손으로 돌린 사람이다
   logs/         Mediator 에 봉인된다.  삭제가 막히고 함대의 다른 사람이 GET 으로 읽는다
```

⑲ 가 링을 끈 근거는 「링은 노드 디스크에 파일로 남는다」 하나였다.

A) **링은 본문 그대로** — 단계마다 비우는 오늘의 링 규약(앞 팩 §6.3) 위에
원문을 흘린다. CB1 이 글자 그대로 선다. 노드 소유자의 디스크에 512 KiB 의
사건 원문이 단계 동안 앉고 다음 단계가 덮는다. (권장)

B) **링도 껍데기** — ⑲ 의 넷째 길을 그대로 쓴다. 노드 디스크에 본문이 0 이다.
**CB1 의 「읽을 수 있는 문장」을 「읽을 수 있는 사건 열」로 고쳐야 한다** —
그러면 이 팩이 사내 실측에서 막고 있던 것이 안 풀린다.

C) **본문이되 끄는 스위치를 둔다** — 기본은 본문이고 정책 파일로 끌 수 있다.
짝 팩의 ⑩ 이 같은 종류의 스위치를 **안 두는 쪽**으로 정한 선례가 있다
(「누가 켜는지도 언제 지우는지도 정할 자리가 없다」).

## Question 3 — 이 회차를 어디까지 도나, 그리고 몇 손인가

짝 팩은 이 질문에 **B**(Inception 을 돌고 그대로 Construction 까지 한

# 확인된 사실 — 묻지 않고 적는 것

착수 전에 팩이 적은 코드 상태를 오늘 코드에 그대로 댔다. **다섯이 뒤집혔고
넷은 범위가 줄거나 값이 정해지는 방향이라 묻지 않는다.**

## 사실 1 — 3.1 의 절반이 이미 `main` 에 있다

```go
// internal/enode/claude.go:343
args := []string{"-p", "--output-format", "stream-json", "--verbose"}
```

짝 팩의 ⑮ 가 가져갔다. `features.md` 3.1 의 첫 항목(「어댑터 인자를 바꾼다」)은
**할 일이 아니라 이미 된 일**이다. 남는 것은 `Decode` 하나다.

```go
// internal/enode/claude.go:412 — 아직 배치다
b, err := io.ReadAll(r)
h := ParseClaude(b, exitCode)
emit(Event{Kind: EventFinal, Text: h.Message})
```

`claude.go` 의 접점도 그만큼 준다 — `Argv` 는 짝 팩이 이미 지났고 이 팩은
`Decode` 만 만진다.

## 사실 2 — 하네스 단계의 링 tee 가 꺼져 있다

`runner.go:186` 이 그 자리이고, `claim.go:794` 는 `Transcript: w.transcript()`
를 **여전히 넘긴다** — 받는 쪽이 안 쓴다. 되살리는 것이 이 팩의 일이라고
⑲ 가 이름으로 적었다 (질문 2).

## 사실 3 — `AppendLog` 의 상한이 청크 아래서 뜻을 잃는다

```go
// internal/record/record.go:57
n, err := io.Copy(f, io.LimitReader(r, limit))   // limit 이 호출마다다
...
if n == limit { fmt.Fprintf(f, "\n... log truncated at %d bytes\n", limit) }
return n, nil                                     // 이번 호출의 바이트 수다
```

오늘은 단계마다 한 번 부르므로 `MaxBlobBytes`(기본 10 MiB)가 단계 상한이다.
청크로 바꾸면 **청크마다 10 MiB** 가 되어 상한이 사실상 사라지고, 잘림 표시가
파일 중간에 여러 번 박힌다. 팩의 3.4 는 「상한과 잘림 표시는 오늘 그대로」인데
**「오늘 그대로」가 청크 아래서 뜻이 바뀐다.**

교정 — `AppendLog` 는 **파일의 총 길이**를 기준으로 상한을 걸고 그 총 길이를
돌려준다. 팩의 3.4 가 요구하는 PUT 응답(`{"bytes": <총 길이>}`)이 그 값을
그대로 쓴다. 팩의 뜻 안이라 묻지 않는다.

## 사실 4 — `runctl mcp` 가 `main` 에 없다

`cmd/runctl/` 은 `main.go` · `shape.go` 둘뿐이다. 3.7 은 **이월**이고 CB5 는
보류가 아니라 「해당 없음」이다 (`scene-gates.md` 2절이 그 말을 미리 적었다).

## 사실 5 — 명령 단계와 하네스 단계의 `logs/` 가 다르다

```text
   명령 단계    claim.go:647   buf 를 원문 그대로 올린다.  링에도 원문이 흐른다
   하네스 단계  claim.go:796   selectLogs 를 지난 껍데기를 올린다.  링은 꺼져 있다
```

팩의 3.4 는 「명령 단계는 같은 경로다」로 둘을 하나로 본다. 오늘은 아니다.
질문 1 의 답이 하네스 단계에만 걸리고 명령 단계는 그대로 원문이다 — 이
비대칭은 짝 팩의 ⑰ 이 **잔여로 이미 적어 두었다.**

## 사실 6 — 라우트 셈이 맞는다

`internal/api` 전체의 등록은 **26** 이고 `api.go` 한 파일의 `mux.HandleFunc`
는 **17** 이다. `GET /v1/runs/{run}/steps/{seq}/log` 는 없다 — 3.5 는 신규가
맞다. CB0 이 재는 `grep -c 'mux.HandleFunc' internal/api/api.go` 는
**17 -> 18** 이 된다.

# 이 문서가 닫히면

질문 셋의 답을 받아 `requirements.md` 를 낸다. **질문 1 과 2 의 답이
`scene-gates.md` 의 CB1 · CB2 · CB3 · CB4 문구를 다시 쓰게 한다** — 수용
기준이 오늘 코드에서 못 서는 채로 남으면 그것이 짝 팩의 CP6 이 닫힌 방식과
같은 자리가 된다.
