## 1.1 왜 지금인가

사내 실측(2026-09-11)이 둘을 봤다. 제어판의 트랜스크립트 카드가 에이전트 단계가
도는 내내 비어 있고, 중앙 현황판에는 실시간 트랜스크립트가 아예 없다.

앞 회차가 그 둘을 이월로 적었고 `ADR-025` §7 ③ 이 **여는 조건**을 미리 적어
두었다 — 「로그를 실행 중에 봐야 하는 사례가 나올 때」. 사내 실측이 그 사례다.

## 1.2 가치의 고정점

`scene-gates.md` 1절의 장면 하나다.

**계약을 던지고 제어판과 현황판을 열면, 단계가 끝나기 전에 읽을 수 있는 문장이
흐르고, 도구 호출이 이름으로 보이며, 끝난 뒤에도 같은 모양으로 읽힌다.**

「읽을 수 있는 문장」이 이 회차의 값이다. 사건 종류만 흐르는 화면은 이 값을
못 낸다 — 질문 2 가 그것을 재는 자리였다.

# 2. 착수 전 실측 — 팩을 코드에 댔다

팩은 2026-09-11 에 썼다. 짝 팩(`v3-run-harness-components`)이 그 뒤 유닛 다섯을
`main` 에 넣으면서 **이 팩의 전제 다섯이 뒤집혔다.** 아래가 그 다섯과 처리다.

## 2.1 3.1 의 절반이 이미 있다

```go
// internal/enode/claude.go:343
args := []string{"-p", "--output-format", "stream-json", "--verbose"}
```

짝 팩의 결정 ⑮ 가 가져갔다. 게이트 CA1 · CA4 · CA5 가 `system/init` 줄을
재는데 `--output-format json` 아래서는 그 줄이 안 나와서다.

남은 것은 `Decode` 하나다 — 아직 `io.ReadAll` 로 배치다 (`claude.go:412`).
**접점이 줄었다** — `claude.go` 의 `Argv` 는 짝 팩이 이미 지났고 이 회차는
`Decode` 만 만진다.

## 2.2 하네스 단계의 링 tee 가 꺼져 있다

짝 팩의 결정 ⑲ 가 `runner.go:186` 에서 껐다. 근거는 ⑮ 이 켠 stream-json 아래서
사건 전문이 노드 디스크의 512 KiB 파일에 남기 때문이다. 같은 결정이 **되살리는
일을 이 회차의 몫으로 이름 지어 남겼다** — 「짝 팩이 사건 스트림을 나르면서
노출 정책을 함께 정한다」.

`claim.go:794` 는 `Transcript: w.transcript()` 를 **여전히 넘긴다.** 받는 쪽이
안 쓴다. 되살리기는 그 줄을 다시 잇는 일이다.

## 2.3 `logs/` 는 원문이 아니다 — 팩의 세 문장이 거짓이 됐다

짝 팩의 결정 ⑰ · ⑱ 이 `selectLogs` 를 넣었다 (`runner.go:315`). 하네스 단계의
`logs/NN-*.log` 에 남는 것은 이것뿐이다.

```text
   전문으로 남는다   system/init 사건 한 줄 · 마지막 result 사건 한 줄 · stderr
   껍데기로 남는다   그 밖의 모든 사건 — type · subtype · 도구 이름 · 성공 여부 · 토큰 수
   표시한다         걷었음을 한 줄로.  {"type":"enode.elided","events":N,"bytes":B}
   안 남는다        본문.  assistant 의 text 도 thinking 도 도구 결과도 같다
```

그래서 팩의 세 문장이 오늘 코드에서 거짓이다.

```text
   3.4 보안 요구    「오늘도 logs/ 에 원문이 봉인된다.  이 팩은 시점만 앞당긴다」
   constraints 4    「원문이 봉인이다 (ADR-005)」
   3.2 수용 기준    「링에서 읽든 record 에서 읽든 같은 사건 열이 나온다」
```

**팩의 잘못이 아니다** — 팩은 09-11, ⑰ · ⑱ 은 09-12 의 사용자 결정이다.
이 회차는 그 결정을 되돌리지 않는다 (질문 1 의 C 를 안 골랐다).

## 2.4 `AppendLog` 의 상한이 청크 아래서 뜻을 잃는다

```go
// internal/record/record.go:64 ~ :73 (AppendLog 의 선언은 :57)
n, err := io.Copy(f, io.LimitReader(r, limit))   // limit 이 호출마다다
if n == limit { fmt.Fprintf(f, "\n... log truncated at %d bytes\n", limit) }
return n, nil                                     // 이번 호출의 바이트 수다
```

**`n == limit` 자체가 틀렸다** (U3 의 Functional Design 이 찾았다). 딱 맞았을
때도 참이고 여러 번 부르면 여러 번 박힌다. **옳은 패턴이 같은 파일에 이미 있다** —
`WriteBlob` 이 `limit+1` 을 읽고 `n > limit` 로 센다 (`record.go:287` · `:292`).
이 회차는 진행 파일에 옳은 쪽을 쓰고 **`AppendLog` 의 오판은 코드의 잔여로 남긴다**.

오늘은 단계마다 한 번 부르므로 `MaxBlobBytes`(기본 10 MiB)가 단계 상한이다.
청크로 바꾸면 **청크마다 10 MiB** 가 되어 상한이 사실상 사라지고 잘림 표시가
파일 중간에 여러 번 박힌다. FR-5 가 이것을 고친다.

## 2.5 `runctl mcp` 가 `main` 에 없다

`cmd/runctl/` 은 `main.go` · `shape.go` 둘뿐이다. 3.7 은 **이월**이고 CB5 는
보류가 아니라 「해당 없음」이다.

## 2.6 명령 단계와 하네스 단계가 다른 경로다

```text
   명령 단계    claim.go:647   buf 를 원문 그대로 올린다.  링에도 원문이 흐른다
   하네스 단계  claim.go:796   selectLogs 를 지난 껍데기를 올린다.  링은 꺼져 있다
```

팩의 3.4 는 「명령 단계는 같은 경로다」로 둘을 하나로 본다. 오늘은 아니다.
이 회차의 변경은 하네스 단계에만 걸리고 명령 단계는 그대로다 — 짝 팩의 ⑰ 이
그 비대칭을 잔여로 이미 적었다.

## 2.7 라우트 셈

`internal/api` 전체의 등록은 **26**, `api.go` 한 파일의 `mux.HandleFunc` 는
**17**. `GET /v1/runs/{run}/steps/{seq}/log` 는 없다. CB0 이 재는 값은
**17 -> 18** 이다.

# 4. 기능 요구사항

팩의 3.1 ~ 3.7 을 여덟로 다시 가른다. 팩이 3.1 안에 묻어 둔 링 되살리기가
질문 2 의 답을 받아 자기 항목이 됐다.

## FR-1 (팩 3.1) `Decode` 가 사건을 배출한다

- `Decode` 가 줄 단위로 읽어 사건을 `emit` 한다. 시그니처는 안 바뀐다
  (`agent-runtime` R3 이 그렇게 잡아 두었다)
- `HarnessResult` 는 마지막 `result` 줄에서 그대로 나온다. 봉투 파서
  (`ParseClaude` · `lastJSONObject`)는 **안 바꾼다**
- 낯선 줄은 버리지 않고 `raw` 사건으로 넘긴다
- `Argv` 는 안 만진다 — 2.1
- **노드 로그에 본문을 안 싣는다.** 오늘 `Emit` 이
  `log.Debug("harness event", "kind", e.Kind)` 로 종류만 적는다. 그대로 둔다

## FR-2 (질문 2 = A) 링을 되살린다 — 원문 그대로

- `runner.go:186` 의 tee 를 다시 잇는다. `claim.go:794` 가 이미 넘기고 있는
  `Job.Transcript` 를 받는다
- **선별을 링에는 안 건다.** 허용목록은 본문을 안 남기고, 본문이 없으면
  CB1 이 재는 「읽을 수 있는 문장」이 안 선다
- 링의 형식 · 크기 · 세대 · 비우기 · 권한(0600)은 앞 팩 §6.2 · §6.3 그대로.
  **내용만 NDJSON 이 된다**
- 명령 단계의 tee(`claim.go:647` 경로)는 오늘 그대로 흐른다

## FR-3 (팩 3.2) 공용 파서 — 하나를 셋이 쓴다

- 새 패키지 `internal/transcript`. **표준 라이브러리만** 임포트한다.
  `enode` · `panel` · `api` 가 이것을 임포트하고, 이 패키지는 셋 중 어느
  것도 임포트하지 않는다
- 사건 종류와 표시 규칙은 `decisions.md` 2절 — `init` · `text` · `tool_use` ·
  `tool_result` · `result` · `raw`
- **껍데기도 읽는다 (새 요구).** 파서가 받는 입력이 둘이다.

```text
   원문 스트림   진행 파일 · 링.  stream-json 사건 전문
   선별본       봉인된 logs/.  init 전문 · result 전문 · 껍데기 줄 · stderr 꼬리
                그리고 {"type":"enode.elided","events":N,"bytes":B} 한 줄
```

- 껍데기 줄은 본문이 없으므로 그렇게 그린다 — 도구 이름 · 성공 여부 · 토큰 수.
  `enode.elided` 는 「본문 N 개 · B 바이트가 걷혔다」한 줄로 그린다
- 링이 감겨 첫 줄이 잘렸으면 첫 개행 뒤부터 읽는다. 총량이 용량 안이면 처음부터
- 사용자 메시지 안의 `tool_result` 는 그 도구 호출에 붙여 그린다
- **파서는 마스킹을 하지 않고 사건을 버리지 않는다.** 못 읽은 줄은 `raw` 다
- **파서의 입력은 신뢰할 수 없다** (SECURITY-13) — 아는 키만 읽는 방식이다.
  `runner.go` 의 `parseEventLine` 이 이미 그 규율이고 파서가 그것을 이어받는다

## FR-4 (팩 3.3) 제어판 카드

- 「하네스 트랜스크립트」 카드가 파싱된 사건을 그린다. 원문 토글이 JSON 줄을
  그대로 보인다. 1초 폴링 · 세대가 바뀌면 비우기 · 밀렸다는 표시는 앞 팩 그대로
- 「지난 작업」의 봉인된 트랜스크립트는 같은 파서를 거친다. 출처를 FR-6 의
  GET 라우트로 바꾼다 — tar 를 통째로 풀던 우회를 걷는다. `verdict` 는 지금처럼
  Run 목록에서 온다
- **봉인 전과 뒤를 화면이 가른다.** 봉인 뒤의 사건 열에는 본문이 없다.
  「본문 N 개가 걷혔다」가 화면에 적혀 있어야 한다 — 없으면 읽는 사람이
  「에이전트가 아무 말도 안 했다」로 읽는다
- 데몬 로그 카드는 그대로 옆에 있다
- **사건 본문은 텍스트로만 그린다** (SECURITY-05) — 하네스 출력은 신뢰할 수
  없는 입력이다. `page.go` 가 이미 `textContent` 와 `esc()` 를 쓰고 있다

## FR-5 (팩 3.4 · 질문 1 = B) 노드가 원문 청크를 진행 파일에 올린다

- 노드는 링에 쓰는 것과 같은 tee 한 겹에서 새 바이트를 모아 올린다.
  주기는 `decisions.md` 2절 — 새 바이트가 있으면 2초, 64 KiB 가 쌓이면 즉시
- **올라가는 자리가 `logs/` 가 아니다.** 진행 파일은 봉인 묶음에 안 들어가는
  별도 파일이다. 이름과 자리는 Application Design 이 닫는다 (8절)
- **단계 끝의 업로드는 오늘 그대로다** — `claim.go:796` 이 `selectLogs` 의
  결과를 `logs/` 에 올린다. 파일이 둘이므로 **두 벌이 안 생기고, 팩이 요구한
  「꼬리만 올린다」가 필요 없어진다**
- 응답이 그 진행 파일의 **총 길이**를 돌려주고 노드가 그 값으로 오프셋을
  맞춘다. 실패한 청크는 다음에 이어 보낸다. **실패가 실행이나 링을 막지 않는다**
- **상한은 총 길이로 건다** (2.4 의 교정). `MaxBlobBytes` 를 넘으면 청크를 더
  올리지 않고 노드 로그에 남긴다. 잘림 표시는 한 번만 박힌다
- 새 라우트를 안 만든다 — 기존 `PUT .../log` 에 쿼리 하나를 더해 가른다.
  모양은 Application Design 이 닫는다

## FR-6 (팩 3.5) Mediator 가 진행 로그를 낸다 — 폴링 GET 하나

- `GET /v1/runs/{run}/steps/{seq}/log?from=<바이트>` **신규 라우트 하나**.
  응답은 그 오프셋부터의 바이트이고 헤더 `X-Enode-Log-Bytes` 에 총 길이를 싣는다.
  `as=events` 면 FR-3 의 파서를 거친 사건 배열이다
- **봉인 전에도 답한다.** 이것은 Record 가 아니다 (`I4` · `ADR-025` §5).
  `GET record` 의 `409` 는 그대로다
- **봉인 전후로 답의 출처가 갈린다.**

```text
   봉인 전   진행 파일.  원문이다
   봉인 뒤   logs/NN-*.log.  선별본이다.  진행 파일은 봉인 때 지워졌다
```

- **그 갈림이 응답에 적혀 있다** (새 요구). 헤더 하나로 출처를 말한다 —
  이름은 Application Design 이 닫는다. 없으면 읽는 쪽이 두 바이트열을 같은
  것으로 읽고, `from` 오프셋을 그대로 이어 쓰다가 엉뚱한 자리를 읽는다
- 아직 파일이 없으면 총 길이 0 에 빈 본문이다. 없는 Run 은 `404`
- 보호 규칙은 `GET /v1/runs` 와 같다. 판정을 싣지 않는다 (`ADR-065`)
- `api.go` 는 등록 줄 하나만 는다. 핸들러는 새 파일이다
- 입력을 검증한다 (SECURITY-05) — `seq` 는 양의 정수, `from` 은 음이 아닌
  정수, `as` 는 `raw` · `events` 둘뿐이다. 그 밖은 `400`

## FR-7 (팩 3.6) 중앙 현황판 — Run 상세의 단계 카드

- Run 상세에 단계마다 트랜스크립트 카드. 도는 단계는 폴링으로 자라고 끝난
  단계는 한 번 읽는다. 간격은 2초, **목록 폴링(5초)과 별개 타이머**다
- 표시 규칙은 제어판과 같다 (FR-3). 원문 토글이 있다. 봉인 전과 뒤를 가른다
- 그 카드가 그래프와 목록을 가리지 않는다
- 화면은 이 회차의 새 `.pen` 으로 진행자가 그린다 — S2 의 확장이다
- `/ui/` 의 보안 헤더 다섯은 이미 걸려 있다 (`ui.go:64-71`). 그대로 탄다
- **사건 본문은 텍스트로만 그린다** (SECURITY-05)

## FR-8 (팩 3.7) Mediator MCP 도구 `run.log` — 이월

`runctl mcp` 가 `main` 에 없다 (2.5). **이월**이고 CB5 는 「해당 없음」이다.

## 5.1 차단 게이트 다섯 — 그대로 걸린다

## 5.4 SECURITY-03 — 준수의 범위와 잔여

짝 팩의 ⑰ 이 이 규칙을 이 저장소에 처음 걸었고, 그때 해악 모델은
**「봉인되어 삭제도 막힌다」**였다. 이 회차는 그 표면을 **넓히지 않는다.**

```text
   안 넓힌다   봉인되는 logs/ 는 오늘 그대로 선별본이다.  ⑱ 을 안 무른다
               노드 로그에 본문을 안 싣는다 (FR-1)
   넓힌다      진행 파일    Mediator 디스크.  도는 동안만.  봉인 때 지워진다
               링          노드 디스크.  512 KiB · 0600 · 단계마다 덮인다
```

**잔여를 이름으로 적는다 — 셋이다.**

```text
   ①  도는 동안 Mediator 디스크에 원문이 앉는다.  봉인 때 지워지지만
       그 사이에 비밀이 찍혀 있을 수 있다
   ②  그동안 GET log 를 부를 수 있는 사람이 그것을 읽는다.  이 시스템에는
       주체별 권한 모델이 없다 — 토큰 하나다.  「그 Run 의 요청자만」으로
       좁히려면 그 모델을 새로 만들어야 하고 팩 밖이다
   ③  링에 원문이 노드 디스크에 앉는다.  읽는 사람이 그 기계의 소유자이고
       그 에이전트를 자기 손으로 돌린 사람이다.  단계마다 덮인다
```

**셋 다 사용자가 질문 1 · 2 에서 값을 보고 고른 것이다.** ① 과 ② 를 없애는
길은 질문 1 = A(중앙도 껍데기)였고 그것을 고르면 CB4 가 죽는다. ③ 을 없애는
길은 질문 2 = B 였고 그것을 고르면 CB1 이 죽는다.

**막는 것을 함께 적는다** — 이 회차가 넣는 것이다.

```text
   진행 파일은 봉인 때 지운다        영속하는 자리에 본문이 안 남는다
   진행 파일에 총 길이 상한을 건다   FR-5.  MaxBlobBytes
   진행 파일의 권한은 0600          Mediator 프로세스만
   링은 0600 이고 단계마다 덮인다     오늘 그대로 (transcript.go:65)
   GET log 는 GET /v1/runs 와 같은 보호  FR-6
   제어판은 루프백.  노출하면 토큰을 요구한다  오늘 그대로 (panel.go:59)
   노드 로그에 본문을 안 싣는다       FR-1
```

## 5.5 SECURITY-04 — 제어판 페이지에 헤더를 건다

`/ui/` 는 다섯 헤더가 다 걸려 있다. **제어판 페이지(`page.go:15`)에는 `Content-Type`
뿐이다.** 오늘까지는 자기 화면만 그렸으므로 기존 사실이었는데, 이 회차가 그
페이지에 **신뢰할 수 없는 하네스 출력을 그린다.** 위험을 이 회차가 들여오므로
이 회차가 닫는다 — `ui.go:64-71` 과 같은 다섯 줄이다.

**범위가 느는 자리라 이름으로 적는다.** 빼려면 이 절을 지우고 5.3 의
SECURITY-04 판정을 다시 센다.

## 5.6 오용 시나리오 (SECURITY-11)

```text
   ①  에이전트가 자격증명을 읽어 도구 결과에 싣는다
       -> 봉인에는 안 남는다 (⑱).  도는 동안 진행 파일과 링에는 있다 (5.4 ① ③)

   ②  하네스가 거대한 줄 하나를 뱉어 파서를 먹인다
       -> 파서는 줄 단위이고 표시 상한이 있다 (tool_result 앞 500자).
          진행 파일은 총 길이 상한을 탄다 (FR-5)

   ③  하네스가 JSON 처럼 보이는 낯선 줄을 뱉는다
       -> raw 로 남는다.  버리지도 실행하지도 않는다 (FR-3)

   ④  사건 본문에 HTML 이나 스크립트가 들어 있다
       -> 화면이 텍스트로만 그린다 (FR-4 · FR-7).  CSP 가 한 겹 더다 (5.5)

   ⑤  노드가 봉인된 Run 에 청크를 민다
       -> 410 이다.  오늘 putLog 가 이미 그렇게 한다 (api.go:879)

   ⑥  누가 GET log 를 남의 Run 에 부른다
       -> 오늘의 권한 모델에서 막히지 않는다.  5.4 ② 가 그 잔여다
```

# 6. 수용 기준 — 고쳐 쓴 장면 조각 게이트

`scene-gates.md` 의 CB0 ~ CB6 을 2.3 의 사실과 3절의 답 위에서 다시 쓴다.
**고친 것은 CB2 하나이고 나머지는 잴 것이 는다.**

| | 조각 | 확인 | 팩에서 바뀐 것 |
|---|---|---|---|
| CB0 | 기동이 안 깨졌다 | `grep -c 'mux.HandleFunc' internal/api/api.go` 가 **17 -> 18** | 값이 실측으로 박혔다 |
| CB1 | 흐른다 | 단계가 끝나기 전에 **읽을 수 있는 문장**이 흐르고 도구 호출이 이름으로 보인다. 512 KiB 를 넘겨도 안 깨지고 첫 줄이 잘린 채로도 파싱된다. 다음 단계 첫 줄에 갈린다. 원문 토글이 JSON 줄을 보인다 | 그대로. **질문 2 = A 가 이것을 살렸다** |
| CB2 | 읽힌다 | 끝난 Run 을 제어판 지난 작업에서 누른다. 같은 파서의 같은 모양이다. 출처가 GET 이고 tar 를 안 푼다. `verdict.checks` 는 그대로 보인다. **본문이 없고 「N 개가 걷혔다」가 화면에 적혀 있다** | **고쳤다.** ⑱ 이 본문을 걷었고 이 회차가 못 되돌린다. 「같은 모양」은 서고 「같은 내용」은 안 선다 |
| CB3 | 올라간다 | 도는 동안 `curl` 로 두 번 부르면 총 길이가 늘어 있다. PUT 을 한 번 실패시켜도 다음 청크가 이어 붙고 두 벌이 안 생긴다. 봉인 뒤 tar 의 로그와 GET 의 답이 같은 바이트다. **봉인 전 마지막 GET 의 바이트와 봉인 뒤 GET 의 바이트는 다르고, 그 갈림이 응답 헤더에 적혀 있다.** `GET record` 는 봉인 전 `409` 그대로 | 잴 것이 하나 늘었다 |
| CB4 | 보인다 (중앙) | 현황판 Run 상세의 단계 카드에 제어판과 **같은 문장**이 같은 시각 흐른다. 목록 폴링을 멈춰도 카드는 자란다. 원문 토글이 있다 | 그대로. **질문 1 = B 가 이것을 살렸다** |
| CB5 | 도구 | **해당 없음.** `runctl mcp` 가 `main` 에 없다 (2.5) | 보류가 아니라 해당 없음으로 닫는다 |
| CB6 | 한 장면 | `scene-gates.md` 1절 ① ~ ⑦ 을 끝까지. **⑥ 의 「같은 바이트」는 봉인 뒤 기준으로 읽는다** | ⑥ 의 읽는 법이 박혔다 |

**눈 검증을 보류로 넘기지 않는다.** CB1 · CB4 는 사람이 실제 하네스로 보는
것이 곧 게이트다 — 짝 팩의 CP6 이 코드 게이트만 초록인 채로 닫혔고 사내 실측이
그 첫 눈이었다. 이 팩이 그 대가다.

# 8. Application Design 이 닫을 것

**사람에게 물을 것이 아니다.** 답이 설계에서 나온다.

```text
   ①  진행 파일의 이름과 자리.  run-<id>/ 안이면 Seal 이 tar 하기 전에 지워야
      한다 — blobs/ 의 .tmp- 를 걷는 선례가 record.go:112 에 있다
   ②  청크 PUT 을 기존 라우트에서 어떻게 가르는가.  쿼리 하나가 권장이다.
      CB0 의 셈(17 -> 18)이 그 전제다
   ③  봉인 전후의 출처를 말하는 응답 헤더의 이름
   ④  AppendLog 의 시그니처 — 총 길이를 돌려주고 총 길이로 상한을 건다.
      기존 호출자(putLog)가 안 깨져야 한다
   ⑤  selectLogs 가 FR-3 의 파서를 쓰는가, 아니면 그대로 두는가.
      「파서는 하나다」가 요구하는 자리이나 selectLogs 는 짓는 쪽이고
      파서는 읽는 쪽이라 같은 물건이 아닐 수 있다
   ⑥  유닛 분해와 파일 행렬.  Units Generation 의 몫이고 팩이 그것을
      명시로 요구했다 (constraints 접점 절)
```

# 9. 회차 운영 — 질문 3 = B

```text
   Inception     aidlc-docs/v3-run-transcript/.  브랜치 v3-run-transcript
   Construction  aidlc-docs/taeels/.  유닛마다 unit/<유닛> 브랜치
   손            하나 (taeels).  짝 팩과 같은 모양이다
   병합          둘 다 PR 로 main.  유닛은 그 유닛의 장면 게이트가 초록인 뒤에
   User Stories  **돈다.** 이 팩은 화면 둘을 바꾸고 사용자 워크플로에 닿는다 —
                 core-workflow.md 의 「ALWAYS Execute」 지표에 걸린다.
                 짝 팩이 이 자리를 스킵했고 검증이 규칙 위반으로 셌다
```

접점은 하나로 줄었다 — 짝 팩이 `Argv` 를 이미 가져갔으므로 `claude.go` 에서
겹치는 것이 없고, `runner.go` 와 `claim.go` 는 이 팩만 만진다.
`internal/api/api.go` 의 등록 줄은 여느 유닛과 같은 직렬 병합이다.
