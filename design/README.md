# 화면 — 무엇을 그렸고 왜 그렇게 그렸나

`enode-ux.pen` 이 원본이고 `exports/` 가 거기서 내보낸 그림, `index.html` 이
그림을 한 장에 모은 페이지다. 이 문서는 **그리는 규칙**이다. 구현 사양이 아니다 —
값은 `../requirements/decisions.md` 가 갖고 필드 노출은 `enode-design` 의
`ADR-065` 가 정한다.

```text
   enode-ux.pen        원본.  화면 아홉 장 + 컴포넌트 다섯
   exports/*.png       화면 아홉 장 + C1 · C2
   index.html          모아 보는 페이지
```

# 1. 표면 둘의 책임이 다르다

```text
   중앙 현황판     Mediator 가 embed 로 내보낸다 (GET /ui/).  함대 전체를 본다
                  자료 출처는 GET /v1/nodes · GET /v1/runs
                  읽기 전용.  조작은 하지 않는다

   호스트 제어판   enodectl serve 가 이 기계에 띄운다.  자기 노드 하나를 본다
                  자료 출처는 로컬 프로세스 + Mediator 조회
                  조작한다.  start · stop · drain · 로그
```

둘이 같은 노드를 봐도 보이는 것이 다르다. 그 차이가 UX 의 뼈대이므로 4절에
규칙으로 적는다.

---

# 2. 노드 카드 — 두 표면이 공유하는 원자 단위

카드가 그려야 할 상태는 여섯이다.

```text
   상태                      중앙   호스트   카드가 말해야 하는 것
   ───────────────────────   ────   ─────   ──────────────────────────────
   ① 광고 중 · 임대 없음      보임    보임    무엇을 할 수 있는가 (capabilities)
   ② 임대 중                 보임    보임    어느 Run · 언제 풀리나 (not_after)
   ③ draining                보임    보임    어느 모드인가 · 진행 중인가 대기 중인가
   ④ 광고 만료 임박           보임    보임    expires_at 까지 남은 시간
   ⑤ 프로세스 멈춤            안 보임  보임    멈췄다는 사실 + start 버튼
   ⑥ 사람을 기다림            보임    보임    누가 답하나 · 물은 지 얼마나 · 칠 명령
```

## 2.1 ⑤ 가 두 표면을 가르는 자리다

`ADR-065` 는 「만료되지 않은 광고만 낸다. 죽었지만 아직 만료되지 않은 노드는
잠깐 남을 수 있다」고 못 박았다. 중앙이 보는 것은 살아 있음이 아니라 광고의
잔존이다.

```text
   중앙에서 노드가 죽으면      즉시 사라지지 않는다.  광고가 만료될 때까지 남고
                             그 뒤 격자에서 조용히 빠진다

   호스트에서 노드가 죽으면    즉시 보인다.  프로세스를 직접 보기 때문이다
                             그리고 수용 기준이 start 로 띄우기를 요구한다
```

**화면은 이 지연을 숨기면 안 된다.** 중앙 카드에 `observed_at` 과 `expires_at`
을 함께 얹어서, 보고 있는 것이 관측 시각의 사실이지 지금의 사실이 아님을
드러낸다. 만료가 가까운 카드는 흐려져서 ⑤ 로 넘어가는 중임을 예고한다.

## 2.2 ③ 은 두 국면이다

drain 은 소유자가 명시적으로 풀어야 후보로 돌아온다. 도는 Run 이 경계에서 끝나도
자동으로 안 풀린다. 그래서 draining 카드는 **두 국면**을 가른다.

```text
   draining · 진행 중    아직 도는 작업이 있다.  경계를 기다린다          C4
   draining · 대기 중    다 끝났다.  소유자가 풀기만 하면 된다             C5
```

이 둘을 안 가르면 사람이 화면만 보고는 「지금 되찾았나」를 모른다. CP3 · CP4 의
화면 검증(`../requirements/scene-gates.md` §2.1)이 이 배지를 본다.

## 2.3 ⑥ 은 기계가 아니라 사람을 기다린다

`ASKED` 인 동안 `reap` 이 `not_after` 를 일부러 무시한다 (`ADR-047`). 그래서
②의 카운트다운을 그대로 쓰면 **0 아래로 내려간다.** 카드는 갈라져야 한다.

```text
   ② 임대 중          02:41 남음        기계의 시간.  하트비트가 미는 값
   ⑥ 사람을 기다림     기한 없음         ask.deadline 이 있으면 그것.
                                        없는 것이 정상이다 — ADR-032 가
                                        「사람의 시간을 시스템이 짐작하지
                                        않는다」로 무한 대기를 정했다
```

중앙은 **답을 받지 않는다.** 카드는 누가 답할 수 있는지(`answerers`)를 적고,
칠 명령은 Run 목록 아래 안내 상자가 진다 (`decisions.md` 7.2 의 B+C).

# 3. 화면 아홉

```text
   S0   토큰 입력              중앙    최초 1회.  Mediator Bearer 토큰
   S0b  토큰 입력 · 401         중앙    토큰을 거절당한 상태
   S1   함대 격자              중앙    노드 카드 격자 + Run 목록.  이 화면이 기본이다
   S1b  함대 격자 · 갱신 실패   중앙    폴링이 끊긴 상태.  카운트다운을 멈춰 세운다
   S2   Run 작업 그래프         중앙    S1 에서 Run 을 고르면 열린다
   S3   호스트 제어판           호스트  도는 노드.  신원 · 현재 작업 · drain · 탐지 능력
   S3b  호스트 제어판 · drain   호스트  drain 을 건 뒤.  C3 가 여기 얹혀 있다
   S4   트랜스크립트            호스트  자리만.  전체 화면 판은 안 만든다
                                        트랜스크립트 자체는 범위 안이고 S3 의
                                        카드가 그것을 진다 (constraints.md §5)
   S5   호스트 제어판 · 멈춤    호스트  멎은 노드.  주 동작이 start 다
```

컴포넌트:

```text
   C1   노드 카드                           S1 · S3 이 공유한다
   C2   Run 행                              S1 의 목록
   C3   자원 회수 · 활성 (draining, 자유)     S3 의 「자원 회수」 프레임이 건 뒤에 이것으로 바뀐다
   C4   배지 · draining 진행 중              S1 카드 배지
   C5   배지 · draining 대기 중              S1 카드 배지
```

C3 · C4 · C5 는 2026-09-08 에 화면에 얹혔다 — `scene-gates.md` CP4 가 셋을
전부 눈으로 보라고 요구하는데 export 열 장 어디에도 없었기 때문이다.

```text
   C3   S3b 에 인스턴스로 얹혔다.  「drain 풀기」 버튼이 그 화면에 있다
   C4   S1 의 ws-c 카드.  배지 글자가 「draining · 진행 중」이다
   C5   S1 의 board-02 카드.  배지 글자가 「draining · 대기 중」이다
```

**C4 · C5 는 인스턴스가 아니라 글자로 얹혔다.** 그 둘의 컴포넌트는 solid 배지라
카드의 반투명 배지와 결이 다르고, 카드 안에 끼우면 격자에서 그것만 튄다. 게이트가
보는 것은 배지가 두 국면으로 **갈리는가**이므로 글자로 족하다 —
**구현은 여전히 이 컴포넌트를 조건부로 끼운다.**

S3 과 S5 는 서로 다른 기계다. **S1 의 흐려진 카드와 S5 가 같은 순간의 같은
노드다** — 중앙은 광고가 만료될 때까지 그것을 보이고, 소유자는 데몬이 없다는
것을 지금 본다. CP4(현황판과 제어판이 같은 사실을 보인다)를 이 두 장이 받는다.

## 3.1 S1 함대 격자 — 왜 Run 목록이 같은 화면에 있는가

`QUEUED` 인 Run 은 **어느 노드 카드에도 안 얹힌다** — 얹힐 노드가 아직 없기
때문이다. 카드 격자만으로는 대기가 안 보이고, Run 목록이 같은 화면에 있어야
「보드가 다 찼고 둘이 기다린다」가 한 눈에 읽힌다.

```text
   ┌ 함대 격자 ───────────────────────┐  ┌ Run 목록 ────────┐
   │  카드  카드  카드                 │  │  RUNNING  ...    │
   │  카드  카드  카드                 │  │  QUEUED   ...    │  <- 어느 카드에도
   └──────────────────────────────────┘  │  QUEUED   ...    │     안 얹힌다
                                          └──────────────────┘
```

## 3.2 S2 작업 그래프 — 이미 있는 자료로 그린다

`GET /v1/runs/{id}` 의 `steps[]` 와 `needs[]` 가 그대로 간선이다. 새로 만드는
것은 `StepView.chosen` 하나뿐이다. 노드는 단계, 색은 `state`, 어느 기계에
얹혔는지는 `node` 다.

## 3.3 S3 호스트 노드 카드 — 조작이 있는 유일한 화면

프로세스 제어(`status` · `start` · `stop` · `logs`), 탐지 능력 읽기 전용 표시,
현재 작업(임대 · Run · 단계 이름 · 회차 · 시작 시각), **트랜스크립트와 데몬 로그**,
drain 토글, **지난 작업**, Mediator 마지막 응답 시각이 여기 모인다.

- **탐지 능력에 편집 자리를 만들지 않는다** — 광고는 매번 전부이고 다음 광고가
  덮으므로 화면에서 고쳐도 다음 주기에 사라진다
- **현재 작업의 출처는 Mediator 조회다** (`decisions.md` 2절). 데몬 로그를 읽지 않는다
- **임대 카운트다운을 진행 막대로 그리지 않는다** — `not_after` 는 `renew 60초 ×
  factor 3` 이고 하트비트마다 다시 밀린다. 작업 마감이 아니라 **하트비트 신선도**다.
  막대로 그리면 채워지다 되돌아가고, 사람은 그것을 작업 진행으로 읽는다.
  2026-09-08 에 막대를 걷고 그 사실을 한 줄로 적었다 (`scene-gates.md` CP1)
- **트랜스크립트 카드와 데몬 로그 카드를 나란히 둔다** — `scene-gates.md` CP6 이
  「둘이 다른 물건임이 화면에서 보인다」를 잰다. 하네스가 뱉는 것은 노드의 링 파일
  (512 KiB · 1초 폴링 · Mediator 를 안 거친다)이고, 데몬 로그는 헤더의 「로그」
  버튼이 읽는 것이다. **한 카드로 합치면 그 구분이 사라진다**
- **`정지` · `재시작` 은 누르기 전에 그 Run 이 어떻게 끝나는지 말한다** —
  제어판이 `POST /v1/runs/{id}/cancel` 을 먼저 부른다 (`decisions.md` 7.2).
  안 그러면 소유자가 껐는데 기록에는 하트비트가 끊긴 것으로 남는다
- **지난 작업 목록이 이 화면에 있다** — `decisions.md` 6.5 가 범위로 들였고
  `scene-gates.md` CP6 ②가 잰다. 새 화면이 아니라 S3 안의 카드다.
  목록은 `GET /v1/runs` 를 자기 `node_id` 로 거른 것이고 봉인본은
  `GET /v1/runs/{id}/record` 에서 푼다
- **Mediator 연결 상태를 보인다.** 로컬 기능은 Mediator 가 죽어도 살지만 drain 통보는
  광고를 거쳐야 노드에 닿는다. 그 사실을 화면이 말하지 않으면 「눌렀는데 왜 안 먹히나」
  가 생긴다. S1b 의 짝이다. pen 에는 아직 자리가 없다 — 구현이 더한다

# 4. 두 표면이 같은 노드를 다르게 보이는 규칙

## 4.1 신원 필드

```text
   중앙 카드     label 만.  사람이 읽는 식별은 label 이 한다
                 principal 을 내지 않는다 (ADR-065 결정)

   호스트 카드   node_id · label · principal · instance 전부
                 자기 기계이므로 소유자 식별을 숨길 이유가 없다
```

## 4.2 drain 조작 자리

```text
   중앙     draining 배지만 보인다.  누를 수 없다
   호스트   토글이 있다.  graceful · at-boundary 두 모드를 고른다
            건 뒤에는 현재 모드와 「풀기」가 보인다 (C3)
```

**중앙 배지의 자료 출처는 `GET /v1/nodes` 의 `draining` 필드다.** 그 필드는
`ADR-065` 의 2026-09-04 개정으로 응답에 들어왔다 — 값은 `""` · `graceful` ·
`at-boundary` 이고 노드 정책 파일의 복사본이다 (`../requirements/canon.md` §3).
**화면이 정본보다 앞서간 자리가 아니다** — 결정이 먼저 착지했고 이 그림은
그것을 딛는다.

근거는 소유 증명이다. 중앙 표면에는 「이 노드가 당신 것이다」를 판정할 수단이
없어서, 함대 토큰만 가진 사람이 남의 노드를 비울 수 있게 된다. 그 기계에
접속한 것 자체가 소유의 증거이므로 조작은 호스트에만 둔다.

## 4.3 갱신

둘 다 폴링이다. `SSE` 와 `WebSocket` 은 제약으로 제외되어 있다. 간격과 임계값은
`decisions.md` 2절에 있다. 화면은 값을 그리지 않고 **「마지막 갱신 시각」을
표시하는 자리**를 둔다.

```text
   포트               호스트 제어판만 해당.  중앙은 Mediator 기존 포트에 얹힌다
   GET /v1/runs 응답  목록 열 구성이 이것에 딸린다.  최소 열만 그렸다
   페이지네이션        Run 목록 하단에 자리만 있다.  이번엔 없다
   만료 임박의 임계값   카드가 몇 초 전부터 흐려지는가
   갱신 실패의 임계값   몇 번 실패하면 카운트다운을 멈추는가.  S1b 가 자리다
```

# 6. 어휘 규칙

같은 개념의 이름이 화면마다 달라지지 않도록 규칙 하나를 둔다.

```text
   API 값을 보이는 자리   원문 enum 그대로.  Run 은 RUNNING · QUEUED · SUCCEEDED ·
                        FAILED (저장되는 넷), 단계는 PENDING · CLAIMED · DONE ·
                        FAILED · SKIPPED · ASKED (internal/store/verdict.go)
   범례                  한글과 enum 을 나란히 적어 둘을 잇는다
   노드 카드의 배지        노드에는 상태 enum 이 없다.  관측에서 파생되므로 한글로 적는다
```

`SEALED` 는 Run 상태가 아니다. 봉인은 `ADR-005` 의 별도 행위이고 상태 어휘는
`INVARIANTS` §1.1 의 여덟이다 — `CREATED` · `RESOLVING` · `ALLOCATING` ·
`RUNNING` · `VERIFYING` · `SUCCEEDED` · `FAILED` 에 `QUEUED` 가 2026-09-04 에
`ADR-064` 로 그 표에 올랐다 (`canon.md` §1 이 §1.2 의 유예 해제로 적는다). 그중
코드가 `runs.state` 에 실제로 적는 것은 `RUNNING` · `VERIFYING` · `SUCCEEDED` ·
`FAILED` 와 새로 오는 `QUEUED` 다 (`VERIFYING` 은 `internal/store/reap.go` 의
봉인 경로가 트랜잭션 밖에서 적으므로 조회에 잡힌다).

한때 S1b 가 이 규칙을 어겼다 — 필터 칩과 `gerrit-12188-ps4` 배지가 `SEALED` 를
보이는 글자로 썼다. 2026-09-08 에 둘 다 `SUCCEEDED` 로 고쳤고 프레임 이름도
`Filter SUCCEEDED` 로 바꿨다. **이름표까지 고치는 이유**는 그 이름이 한 번
면제의 근거로 쓰였기 때문이다.

# 7. 화면과 코드 사이 — 구현이 지켜야 할 것
